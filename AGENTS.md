# Working on pigy

`PLAN.md` is the design: architecture, naming, repository layout and what each phase delivers. Read it before starting a phase. `SYNC.md` is the protocol through which clients keep a copy of a workspace and change it.

## Setup

- Node.js 22 (`.nvmrc`).
- pnpm 12, pinned by `packageManager` in `package.json`. Install it without sudo with `npm install -g --prefix ~/.local pnpm` and make sure `~/.local/bin` is on `PATH`. `corepack pnpm` does not work: the corepack bundled with Node 22 cannot run pnpm 12.
- `pnpm install`

Nothing else: `pnpm dev` needs no configuration, no Google project and no Cloudflare account.

## Commands

Run from the repository root.

| Command | What it does |
| --- | --- |
| `pnpm dev` | Web app with hot reload and the Worker in the local Workers runtime, both on http://localhost:5173. Brings the local database up to date first. No service worker |
| `pnpm build` | Production build of the web app and the Worker into `apps/web/dist`. Fails if the build contains the simulated sign-in, a development key, the simulated push service or the ID of an e2e build, and if the content security policy could not hold for `index.html` |
| `pnpm preview` | Builds for production and serves that build in the local Workers runtime, on http://localhost:4173. Sign-in needs Google credentials, see below |
| `pnpm preview:e2e` | Builds the app that `pnpm e2e` tests and serves it on http://localhost:4173, or on the port of `PIGY_E2E_PORT`, to try a built app by hand. The port must be free |
| `pnpm lint` | Biome lint, format and import order check |
| `pnpm format` | Biome fixes for the above |
| `pnpm typecheck` | `tsc` in every package |
| `pnpm test` | All Vitest suites |
| `pnpm e2e` | Runs `pnpm preview:e2e` on a port that the system chooses, or on the port of `PIGY_E2E_PORT`, then Playwright against it. Fails if what answers on that port is not the build that it started |
| `pnpm icons` | Makes the icons of the installed app from `assets/icon.svg`. Commit what it writes |

One package: `pnpm --filter @pigy/worker test`. One file: `pnpm --filter @pigy/worker test test/health.test.ts`. Watch mode: `pnpm --filter @pigy/core exec vitest`.

A build registers a service worker, which keeps the app on the device: see "The service worker" below. `pnpm preview` and `pnpm preview:e2e` serve on the same address unless `PIGY_E2E_PORT` names another port, so a browser that has opened one of them shows that build once more after the next build, from the device, and the new one from the second page load on. A private window starts from nothing.

Several checkouts on one machine can run `pnpm e2e` at the same time: see "Several checkouts on one machine" below.

`pnpm --filter @pigy/providers conformance:live <network>` is not part of any of these. It posts to a real account, see "Run the conformance suite against a real network" below.

## Several checkouts on one machine

Several checkouts on one machine can run `pnpm e2e` at the same time, each against its own build:

- **Each run has a port of its own.** It is `PIGY_E2E_PORT` if that is set. Otherwise the server of the run chooses a port as it starts, after the build, and says which in its output, where `webServer.wait` in `e2e/playwright.config.ts` reads it. Playwright puts it into the environment before the global setup and before it starts the workers, which make `use.baseURL` of it. No port is chosen before the build, so none waits free during the build for another server to take. The choice and the listening are still two steps: Vite has the system name a free port, lets go of it, and then listens on it, some milliseconds later. A server whose port is taken in between does not start, and the run fails without having tested anything. So does a run that is given a port that is taken.
- **Each run talks to one address.** The server listens at 127.0.0.1 alone, not at `localhost`, which is also ::1. The browser resolves `localhost` to 127.0.0.1 alone, by its resolver rule in `playwright.config.ts`, and the `loopbackOnly` fixture of `e2e/fixtures.ts` makes Playwright's own requests, `page.request` and `context.request`, do the same. So a server at ::1 on the same port is never asked. The app is still addressed as `localhost`.
- **Each run checks that it tests its own build.** Playwright does not notice that its server has stopped, and another server can then take the port. So every e2e build has a random ID of its own, at `/e2e-build.txt`, which the build also says in its output. The run takes the ID from there, with the port, and compares it with what the server on its port serves and with the file in this checkout's build: once the server has started, in `e2e/global-setup.ts`, and before and after every test, in the `ownServer` fixture. The first of these checks is also the wait for the server: it says where it listens before the Workers runtime behind it is ready, and answers nothing until then. It has a minute for that, as long as Playwright gives a server to start, and the run fails if it has not answered by then. The run fails, and says what it found, when its server has stopped, when another server has taken the port, also one with a build of the same code, or when this checkout's build has been built over. The test that found it fails, and so does the run, at its end, also where the test passed when it was tried again. During the run, a server that does not answer, or that answers with an error of its own, a 5xx, is asked twice. Then the test fails and says so, and the run is not said to have tested another server: it is the run's own as far as anybody can tell, stuck, or with a Workers runtime that has stopped. `e2e/server.ts` has the reasons, and `e2e/tests/own-server.spec.ts` tests the check.
- **A checkout runs one at a time.** Its e2e build, its database and the build that `vite preview` serves are one each per checkout. The last is the one that was built last, whatever its mode: each build points `apps/web/.wrangler/deploy/config.json` at itself, and `vite preview` serves what that file names. A second `pnpm e2e` or `pnpm preview:e2e` in a checkout builds over the build that the first one tests and empties its database, and the first then fails, saying that the build has changed. For two runs of the same code at once, make a second checkout.
- `pnpm preview:e2e` started by hand serves at 127.0.0.1 on 4173 unless `PIGY_E2E_PORT` says otherwise, and does not start when the port is taken. `pnpm preview` is not part of this: it takes 4173, or the next port that is free.

## Signing in locally

Sign-in is with Google. Without Google credentials, a simulated Google stands in for it: "Sign in with Google" leads to a page of the app itself, labelled as a simulation, where you say who you are. Any email address works, no password.

- `pnpm dev` after a fresh clone: sign in as `admin@example.com`, which the simulated page offers with one click. It is the admin. Invite other addresses under Settings → Access, then sign in as them the same way.
- To change the admins, or to sign in with the real Google, copy `apps/worker/.dev.vars.example` to `apps/worker/.dev.vars` and follow the comments in it.
- `pnpm preview:e2e` always simulates, with `admin@example.com` as the admin, and starts from an empty database every time. It ignores `.dev.vars`.
- `pnpm preview` serves the production build, which has no simulated sign-in. Without Google credentials in `.dev.vars` its sign-in page says that sign-in is not set up.
- Whoever signs in on a device for the first time lands in their sandbox, which says so in a banner. The switch to live is at the top of the sidebar, in the header on a phone, and in the command palette. "Live and sandbox in the app" below has how the choice works.
- The browser keeps who is signed in under `pigy-session` in `localStorage`, and a copy of each workspace that was opened on the device in an IndexedDB database named `pigy/<user ID>/<workspace ID>`. Which workspace to show is kept under `pigy-workspace`: in `sessionStorage` for the tab, and in `localStorage` for the next tab. Signing out deletes all of it, and every other tab forgets its own choice when it starts again because of that. It leaves the files of the app, which the service worker of a build keeps in a cache named `pigy-app-<version>`: they are nobody's. `pnpm preview:e2e` empties the server's database and not the browser's: after it, the browser holds a session that the server does not know, and the app goes to the sign-in page as soon as it has asked.

Which Google is used is decided per request, in `accessConfig` in `apps/worker/src/auth/config.ts`: the real one if `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` are set. Otherwise the simulated one, if the build has it and the request names a local host, as described below. Otherwise sign-in is refused.

The simulated sign-in signs anybody in as anybody, so it must never be deployed:

- `apps/worker/src/index.ts` builds it in only when the Vite mode is `development`, `test` or `e2e`. In a production build the bundler drops it.
- `pnpm build` runs `apps/web/scripts/check-build.mjs`, which fails if the production build contains it. `pnpm preview:e2e` runs the same script the other way round, to prove that the check still knows what to look for. If you rename something in the simulated sign-in, that run tells you to update the script. The script looks for the development key of the next section in the same way, and for the ID of an e2e build, which the production build has no use for.
- It answers only a request whose URL has a local hostname: `localhost`, a name that ends in `.localhost`, `127.0.0.1` or `[::1]`. That is `isLocal` in `apps/worker/src/auth/config.ts`. The Worker reads the hostname from the URL of the request, which comes from its `Host` header: it says what the client asked for, not where the client is. So a dev or e2e build that is exposed to a network, for example with `vite --host` or through a tunnel, lets anyone who sends a local `Host` header sign in as anybody. Keep those builds on the local machine.

## Connecting accounts locally

Every user has a live and a sandbox workspace. An account that is connected in the live one is a real one. In the sandbox it is one of the simulated accounts of that workspace's own simulated world, and nothing leaves the Worker. `PLAN.md` section 6 has the routes.

- The credentials of a connected account are sealed before they are stored, with the keys in the secret `CREDENTIAL_KEYS`. Without it, `pnpm dev` and `pnpm preview:e2e` seal with a key from the repository, `apps/worker/src/development-keys.ts`, so nothing has to be set up. That key protects nothing. It is built in under the same condition as the simulated sign-in, and must never be deployed. A route uses it only where the app is reached at a local host. The publishing workflow is reached at no address: in a build that has the key, it opens with it what such a route sealed. A production build without `CREDENTIAL_KEYS` refuses to connect accounts, with a 503. `pnpm preview` serves such a build, so it connects accounts only with `CREDENTIAL_KEYS` in `.dev.vars`. The tests do not use the key from the repository either: `setup()` gives the app a key of its own, as a deployment has one, and only a test that passes `developmentCredentialKeys` gets the other.
- To connect a simulated account by hand, run `pnpm dev` and sign in. The empty Drafts screen of the sandbox offers "Connect a simulated account", and so does the Channels screen. The form has the simulated server of the sandbox filled in. The page that it leads to is the consent page of the simulated Mastodon, labelled as a simulation. Choose an account. The browser comes back to `/channels?connect=connected&…`, and the screen takes that out of the address, says what happened and lists the channel. The channel is a row of the synced table `channel`. "Disconnect" on its row removes it, with `DELETE /api/workspaces/<workspace ID>/channels/<channel ID>`.
- To connect a real Mastodon account, switch to live and do the same with the domain of your instance. `pnpm dev` reaches the internet. `pnpm preview:e2e` does not: there every request of a live workspace to a network is answered with an error.
- A simulated Bluesky account is connected the same way, with its handle: the sandbox has `ada.bsky.test`, `grace.bsky.test` and `alan.bsky.test`, and the form has the first filled in. pigy signs what it sends to Bluesky with the keys in the secret `BLUESKY_CLIENT_KEYS`, whose public halves it serves at `/connect/bluesky/client-metadata.json`, its client ID. Without it, `pnpm dev` and `pnpm preview:e2e` sign with a key from `apps/worker/src/development-keys.ts`, under the same rules as the development key above, and `pnpm preview` cannot connect Bluesky accounts, in the sandbox either. A real Bluesky account cannot be connected from a pigy at localhost: Bluesky reads the client metadata from the address of the client, and cannot read it there. The form says what Bluesky answered. `PLAN.md` section 6 has why.
- A simulated LinkedIn account is connected with nothing to type: LinkedIn has one place to sign in. The sandbox has three members, Ada Lovelace, Grace Hopper and Alan Turing, whom LinkedIn addresses by their names. It needs no setup in any build: the simulated LinkedIn of a sandbox has pigy as an application of its own, `sandboxLinkedInClient` in `apps/worker/src/network/linkedin-client.ts`, whose one redirect address is the callback address of the pigy that the browser is at. A real LinkedIn account takes the application that you have made in LinkedIn's developer portal, as `LINKEDIN_CLIENT_ID` and `LINKEDIN_CLIENT_SECRET` in `.dev.vars`, with `http://localhost:5173/connect/linkedin/callback` among its redirect addresses. Without them a live workspace refuses to connect LinkedIn accounts, with a 503.
- A simulated Threads account is connected with nothing to type either: the sandbox has `@ada.sandbox`, `@grace.sandbox` and `@alan.sandbox`, and the simulated Threads has pigy as an app of its own, `sandboxThreadsApp` in `apps/worker/src/network/threads-app.ts`, in every build. A real Threads account cannot be connected from a pigy at localhost: Meta sends a browser back to HTTPS addresses only. It takes a pigy that is deployed, with `THREADS_APP_ID` and `THREADS_APP_SECRET`, and an account that is a tester of the app: see "Deployment". Without the two secrets a live workspace refuses to connect Threads accounts, with a 503.
- The access of a Threads channel, and of a Bluesky one, is renewed by the alarm of its workspace about a week after it was issued, whether or not anybody posts: `apps/worker/src/workspace/renewal.ts`. To see it locally, wait a week, or run the tests of `apps/worker/test/renewal.test.ts`, which move the clock. The alarm is set when an account is connected, when an access is renewed, and when a client says hello.

## Notifications locally

The inbox of the app and the push messages to devices tell of the same things: a post that was not sent, a scheduled post that missed its time and is held, an account that has to be connected again, an access that ends in a week. `PLAN.md` section 13 has the design.

- The inbox needs nothing. Make a post fail in the sandbox, as under "Publishing locally" below, and the Inbox screen has it: in the sidebar on a desktop, behind the bell in the header on a phone.
- Push messages need a service worker, which `pnpm dev` has not: Settings say there that notifications are not available. And they need a push service, which only a real browser has. So they are tried by hand with `pnpm preview`, which serves the production build: put Google credentials and `VAPID_PRIVATE_KEY` into `apps/worker/.dev.vars`, open http://localhost:4173 in Chrome or Firefox, turn "Notifications on this device" on in Settings, and make a post fail in the sandbox. The message goes to the real push service of the browser and comes back to it.
- `pnpm preview:e2e` reaches no real host, so what it sends goes to a simulated push service inside the Worker, `apps/worker/src/simulated-push.ts`, which no browser listens to. A real browser can turn notifications on there. The first message is then answered as for a subscription that is gone, and Settings say that they are off again.
- The key is the secret `VAPID_PRIVATE_KEY`: the output of `openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:P-256 | openssl pkcs8 -topk8 -nocrypt -outform DER | openssl base64 -A`. Without it, `pnpm dev` and `pnpm preview:e2e` sign with a key from `apps/worker/src/development-keys.ts`, under the rules of the other development keys, and `pnpm preview` says that notifications are not set up. A browser subscribes with the public half of the key, so every device has to turn its notifications on again after the key is replaced.
- Sharing to pigy is tried by opening the address that Android opens: `/share?title=…&text=…&url=…`. It needs no Android and no connection. The screen there shows what came, and nothing is a draft before "Save as draft" is pressed.

## Using the API locally

pigy has a REST API under `/api/v1`, which is called with a key. `PLAN.md` section 12 is the design, and the API describes itself: `pnpm dev`, then http://localhost:5173/api/v1/docs for people and `/api/v1/openapi.json` for programs.

- To make a key, run `pnpm dev`, sign in, and open Settings → API. The key is one of the workspace on screen: of the sandbox, where everybody starts, it begins with `pigy_test_`, and what is done with it reaches the simulated networks only. The screen shows the key once.
- To use it:

  ```sh
  KEY=pigy_test_…
  curl -s http://localhost:5173/api/v1/account -H "Authorization: Bearer $KEY"
  curl -s http://localhost:5173/api/v1/channels -H "Authorization: Bearer $KEY"
  # A draft, which shows in the app at once.
  curl -s http://localhost:5173/api/v1/posts -H "Authorization: Bearer $KEY" \
    -H "Content-Type: application/json" -H "Idempotency-Key: $(uuidgen)" \
    -d '{"text": "Hello from curl", "saveToDraft": true}'
  # A post to a channel, now: connect a simulated account first, and take its ID from /channels.
  curl -s http://localhost:5173/api/v1/posts -H "Authorization: Bearer $KEY" \
    -H "Content-Type: application/json" \
    -d '{"text": "Hello from curl", "channelIds": ["<channel ID>"], "mode": "shareNow"}'
  ```

  The answer to the last has the post as `sending`. `GET /api/v1/posts/<post ID>` says what became of it, target by target, and the Simulator screen shows it in the feed of the account.
- A key is refused with a 401 once it is revoked or expired, and when its owner is no longer invited. The keys of an account are revoked when a sign-in finds that it has lost the address it was let in with, and when an admin removes its address from the allowlist: `PLAN.md` section 12. They do not come back with a new invitation. Nothing under `/api/v1` takes the session cookie: a signed-in browser that opens `/api/v1/posts` gets a 401.
- The local runtime counts the requests of a key as the platform does, 120 a minute, and answers a 429 beyond that.

## Publishing locally

A post is published by the publishing workflow, `PublishWorkflow`, which `pnpm dev` and `pnpm preview:e2e` run in the local Workers runtime like the rest of the Worker. `PLAN.md` section 8 has the design, `SYNC.md` section 4 what a client asks for and sees.

- To publish by hand, run `pnpm dev`, sign in, connect a simulated account as above, and write a draft. Under its text the editor lists the channels of the workspace: choose one or more, and press "Publish now", or ⌘↵ or Ctrl+Enter. The editor says next to the choice what a chosen account would refuse, and does not publish until nothing is. The draft leaves the list, and a notice leads to it on the Sent screen, where each delivery shows how far it has come, its error in words, and "Retry" where it failed. In the sandbox, "See it in the simulated feed" leads to the post on the Simulator screen, which shows what every simulated account has published.
- Without a screen, enter this in the console of the browser. It is a small client of the sync protocol: it writes a post, sends it to every channel of the sandbox, and logs the changes as they come.

  ```js
  const { workspaces } = await (await fetch("/api/workspaces")).json();
  const sandbox = workspaces.find(({ environment }) => environment === "sandbox");
  // A UUID version 7, which the ID of a row and of a client has to be.
  const id = () => {
    const time = Date.now().toString(16).padStart(12, "0");
    const random = crypto.randomUUID().replaceAll("-", "");
    return `${time.slice(0, 8)}-${time.slice(8)}-7${random.slice(0, 3)}-8${random.slice(3, 6)}-${random.slice(6, 18)}`;
  };
  const [postId, partId] = [id(), id()];
  const socket = new WebSocket(`${location.origin.replace(/^http/, "ws")}/sync/${sandbox.id}`);
  socket.onopen = () =>
    socket.send(JSON.stringify({ type: "hello", protocolVersion: 2, schemaVersion: 9, clientId: id(), cursor: null, lastMutationId: 0 }));
  let asked = false;
  socket.onmessage = ({ data }) => {
    const patch = JSON.parse(data);
    // Every change, as a client sees it: the targets as they go out.
    console.log(patch.changes, patch.rejected);
    if (asked) return;
    asked = true;
    // The answer to the hello has the channels. The post goes to all of them.
    const channels = patch.changes.filter(({ table }) => table === "channel");
    socket.send(JSON.stringify({ type: "mutate", mutations: [
      { id: 1, name: "post.create", args: { id: postId, partId, text: "Hello from the console" } },
      ...channels.map(({ row }, index) => ({ id: 2 + index, name: "target.add", args: { id: id(), postId, channelId: row.id } })),
      { id: 2 + channels.length, name: "post.publish", args: { id: postId } },
    ] }));
  };
  ```

  The last change that it logs has the post as `sent` and its target with it. `await (await fetch("/api/sandbox/feed")).json()` shows where the post went. `publishNow` in `e2e/sandbox.ts` is the same client, which is how these instructions are tested.
- To see a failure, arm a fault before publishing, on Simulator → Failures in the sandbox: a network, what goes wrong and which request it strikes, posting unless you choose another. Or from the console: `await fetch("/api/sandbox/faults", { method: "POST", headers: { "Content-Type": "application/json" }, body: JSON.stringify({ network: "mastodon", kind: "token-revoked", operation: "publish" }) })`. `GET /api/sandbox/faults` lists the kinds and the requests that each simulated network has. The kinds that a network asks to have tried again, `rate-limit`, `server-error` and `lost-response`, make the workflow wait as long as it would for real: a minute at least. Until then the Sent screen says that the post is sending. Not on LinkedIn, where pigy cannot look for a post: there `server-error` and `lost-response` end the delivery at once as unknown. `rate-limit` ends it as failed, because LinkedIn's limits are for the day and the adapter names the next midnight UTC, unless that is less than an hour away: then the workflow waits for it and posts. Threads has a kind of its own, `slow-processing`: the simulated Threads then takes half a minute to prepare the next post, and the delivery waits for it, asking every ten seconds.
- To try a failed target again, press "Retry" on the Sent screen. A target whose channel needs connecting again offers "Reconnect" first. From the console client, send `{ type: "mutate", mutations: [{ id: <the next number>, name: "target.retry", args: { id: "<target ID>" } }] }` on the same socket.
- To publish a thread, add parts to the draft: "Add part" under the text, or ⌘⇧↵ or Ctrl+Shift+Enter in it. Each part is counted for every chosen account the way its network counts. "Customize for …" above the text gives one chosen account a text of its own, which begins as the post's: that account gets it, and the others the post's. From the console client, `{ id: <the next number>, name: "part.add", args: { id: id(), postId, channelId: null, afterId: partId, text: "Second part" } }` before the `post.publish` adds a part after the first.
- The runs of the workflow are kept in `apps/worker/.wrangler/state` with the rest of the local data. `pnpm preview:e2e` starts without any.

## Layout

| Path | Contents |
| --- | --- |
| `apps/web` | React 19, TanStack Router, Tailwind CSS v4, shadcn/ui, and the service worker and manifest that make it an app to install. Its `vite.config.ts` builds and serves both the web app and the Worker |
| `apps/worker` | Hono app, `wrangler.jsonc`, the D1 schema and its migrations, the Durable Object of a workspace with its own schema and migrations, the workflow that publishes, tests that run in the Workers runtime |
| `packages/core` | Zod schemas and domain code shared by web and Worker. Consumed as TypeScript source, no build step. `src/sync` holds what client and server of the sync protocol share: the synced tables, the mutators and the messages. `src/sync/client` is the client of the protocol, as far as it needs no browser. `src/network` holds what an account may post on a network, how its text is counted, and what in a text is a link, a mention or a hashtag: `links.ts` and `entities.ts`, with the rules at their tops. `src/schedule` holds the time zone maths that the mutators of the queue give a post its time with. `src/api` is the public API: `keys.ts` what the app manages its keys with, and, as the entry point `@pigy/core/api`, `v1.ts` with the schemas of every request and answer and the list of the routes, and `openapi.ts`, which makes the OpenAPI document from those |
| `packages/providers` | The contract between pigy and a network, and the adapters that implement it. Mastodon, Bluesky, LinkedIn and Threads. Consumed as TypeScript source: `@pigy/providers` is the contract, `@pigy/providers/mastodon`, `@pigy/providers/bluesky`, `@pigy/providers/linkedin` and `@pigy/providers/threads` adapters, and `@pigy/providers/card` what reads the page of a link |
| `packages/simulators` | Stand-ins for external services, written from their documentation. So far Google sign-in, Mastodon, Bluesky, LinkedIn, Threads, the push services of the browsers and a small web. Consumed as TypeScript source, one entry point per service: `@pigy/simulators/google`, `@pigy/simulators/mastodon`, `@pigy/simulators/bluesky`, `@pigy/simulators/linkedin`, `@pigy/simulators/threads`, `@pigy/simulators/push`, `@pigy/simulators/web` for the pages that the links of a sandbox lead to, and `@pigy/simulators/world` for what the simulated networks share |
| `e2e` | Playwright tests, and the script that draws the icons with their browser |

Imports:

- `apps/web` imports `@pigy/core`. `apps/worker` imports `@pigy/core`, `@pigy/providers` and `@pigy/simulators`. The apps never import each other. `@pigy/core/api` is for the Worker and the tests: the web app does not import it, so that the shapes of the public API and their descriptions are not in its build.
- `packages/core` imports nothing from the apps or the other packages. It runs in the browser and in the Worker, so it uses only the web-standard APIs that both have, such as `URL`, `crypto` and `TextEncoder`, and no browser-only, Node or Workers APIs.
- `packages/providers` imports `@pigy/core` and nothing from the apps. It runs in the Worker, and in Node for its own tests, so the same limits apply. Its tests, and only its tests, import `@pigy/simulators`.
- `packages/simulators` imports `@pigy/core` and nothing from the apps. It runs in the Worker, and in Node for its own tests, so the same limits apply. It never imports `@pigy/providers`, and the simulator of a network uses nothing of `packages/core/src/network`: it checks what the adapter and pigy's own validation do, so it shares no code with them.
- For all three packages Biome rejects `window`, `document`, `localStorage`, `process` and `Buffer`, and Node modules in the source. The source is type-checked without Node types (`tsconfig.src.json`), the tests with them (`tsconfig.test.json`).
- `e2e` imports no application code.

In `packages/providers/src`: `provider.ts` is the contract, `errors.ts` the one error that an adapter reports a failure with, and what every adapter does with one: `quotable`, `forGood` for a connection that failed, `understanding` for the check of an answer, `publish.ts` the loop that publishes a post step by step, `http.ts` how adapters send a request, `host.ts` which hosts they may send one to when somebody else has named the host. `card.ts` reads the page that a link leads to, for its card: the top of the file has what it asks and what it takes. ## Live and sandbox in the app

Everybody has two workspaces, and the app shows one of them at a time. `PLAN.md` section 7 has what was decided and why. What the code relies on:

- **The choice belongs to the tab.** `chosenWorkspace` in `lib/workspace.ts` is asked by `routes/_app.tsx` on every navigation. A tab goes by what it has in `sessionStorage`. A tab that has nothing there takes what the device remembers in `localStorage`, or the sandbox for somebody who has never chosen, and from then on goes by itself: what is chosen in another tab does not reach it. Both places hold the ID of a workspace, so a choice that somebody else left on the device names no workspace of whoever is signed in and counts as none.
- **The workspace and its data reach the screens together.** `_app.tsx` puts `workspace`, `workspaces` and `store` into the route context in one step, and the shell reads the name of the workspace from there, as the screens read their data from the store. Nothing else may remember which workspace is shown: a second place could say "live" over the data of the sandbox for a moment.
- **A screen starts anew when the workspace changes.** The `Outlet` in `_app.tsx` has the ID of the workspace as its key, so the state of a screen is never carried over. `useSwitchWorkspace` also drops what the address says beyond the screen, such as the draft that is open. The notices belong to no screen, and they are made anew in the same way: `AppShell` in `components/app-shell.tsx` gives the list of the notices and `Rejections` the ID of the workspace as their key. So a notice, and what it offers to do, leaves the page in the step in which the shell changes its name, and a screen has nothing to do for that. A notice of a refused change is not dismissed by it: it is there again when the workspace is. Do not take a notice off the screen for a change of workspace with `toast.dismiss`: the notice library removes a notice over several frames, in which it would stand under the name of the other workspace. One kind of notice stays: one that is for the person and not about a workspace, which `keepOverSwitch` of `lib/notices.ts` makes of it. It is on screen again in the next list, until the person closes it. That is for how something went that the person asked for and has to act on, said to them where they no longer are: the disconnect in `routes/_app/channels.tsx` says so that a network kept the access of an account. Such a notice can be on screen under the name of the other workspace, so it says which workspace it is about, and it offers nothing to do.
- **A tab syncs the workspace that it shows, and goes on syncing one that it has shown.** `workspaceSync` in `sync/workspace-sync.ts` starts a sync once and never stops it before the tab is closed or the person signs out: stopping it would lose the changes that it could not store, and leave the ones it has not sent on the device. `syncUnsent` also starts, when the app loads, the sync of a workspace that is not shown and whose copy holds changes that were never sent. So a tab can hold the sockets of both workspaces. Each copy has its own Web Lock and its own channel between the tabs that have it open.
- **The Simulator is the sandbox's.** The live workspace has no simulated world, so its navigation and its command palette have no Simulator, and the address says that there is nothing at it there, with a button that switches to the sandbox. That is for an address that is typed, kept or opened in a tab that shows live: the switch itself goes to the drafts when the workspace that it changes to does not have the screen that is open, by `hasScreen` of `lib/workspace.ts`, which is the one place that says which workspace has which screen. Nothing is asked of `/api/sandbox` in live: the route renders that screen in place of the sections, which are what ask.
- **A tab says what it holds of the workspace that is not on screen.** The sync indicator is about the workspace on screen. `workspace-sync.ts` keeps the stores that the tab has open, and `useOtherWorkspaceSync` in `lib/workspace.ts` reads the other one: when it holds changes that the tab could not store, or that wait to be sent, the switch says so, with a dot and in the words that the indicator would use. It says nothing while there is nothing to say.
- **The browser asks before a page goes that holds what it could not store.** Such a change is in the memory of its tab and nowhere else, in whichever of the two workspaces. While `unsavedInTab()` counts one, `workspace-sync.ts` listens for `beforeunload`, so closing the tab, loading it again and leaving for the consent page of a network all ask first. For as long, the tab holds the Web Lock that keeps a new version of the app from taking over: see "The service worker". `closeWorkspaceSync` ends both at once, for a tab that starts again because its session is over. Whoever signs out has been asked by the app, with the count of every tab. A session that ends by itself, because it expired or the invitation was withdrawn, waits: see the next point.
- **A session that ends by itself waits for what its tab has not stored.** `sessionOver` in `lib/session.ts` is what a tab does about such an end, once, and both ways to hear of it go through it: `check`, in the tab that asks the server, and the `storage` listener, in the tabs that hear of it from that one. It has three steps, in this order:
  - It records on the device that the session is over, `ended` of what `pigy-session` holds, at once. A tab that is opened from then on asks the server and does not start from the copies, and the other tabs hear now. It also takes the tab off the network, with `stopWorkspaceConnections` of `sync/workspace-sync.ts`: the server goes on serving a socket that was open when a session ended, for up to five minutes, so the tab would otherwise send what it stores during its wait. The stores stay as they are. A navigation in the tab from then on stays in the app: `loadSession` hands out the session that is over while the tab waits, because the sign-in page would end the session and close the stores of the tab that it is shown in.
  - It waits: `savedOrDiscarded`, which is `whenSaved()` of `sync/workspace-sync.ts`, so it is over at once unless a change is being written or could not be written. For the whole wait the tab holds the lock `pigy/unsaved`, `holdUnsaved`, also while nothing has failed. After `saveWaitMs`, two seconds, the tab says that it waits: `SessionEnded` in `components/session-ended.tsx`, a dialog that the root route shows over whatever is on screen and that cannot be closed. It offers to go without the changes, which is the only way that they are discarded: no timer does it. `discardUnsaved` shuts the stores of the tab itself, whatever another tab has done to the session, which also ends the browser's question. That question stays in force until then, for a tab that is closed.
  - It looks at the device again. What a tab found out before a wait may not be true after it, so it acts only if the device still holds the session that it found over, which `key` of the stored session tells, and holds it as ended. Then the tab that asked the server ends the session, `endSession`, and goes to the sign-in page, and a tab that heard of it starts again. Otherwise the tab ends nothing and starts again, as whoever the device now says is signed in. A tab leaves once: `go`.
- **`endSession` deletes the copies only when nothing needs them.** They stay while they hold changes that were not synced, which the sign-in page says, and while another window holds the lock `pigy/unsaved`, or that window would have nothing to store into. The sign-in page calls it on every load, so copies that were kept go when nothing needs them any more. The sign-in page counts what other windows could not store, `unsavedInWindowsOf`, next to what the copies hold, because "Delete these changes" takes both. A window that holds the lock and has not said how many changes it holds is not taken to hold none: it does not answer, because the browser has put it aside, or its write is under way, which no window counts. `unsavedInWindowsOf` says `unknown` then, after the whole time that a window has to answer, and the page warns of changes without a number, or of "at least" as many as were counted, and asks about them in the same words before it deletes.
- **A session is taken on and cleaned up after under one lock.** Deleting the copies is several steps that wait for the browser, and a session that began in their middle would lose what it has stored by then. So `adopt`, `endSession` and `forgetSession` of `lib/session.ts` do their work under the Web Lock `pigy/session`, `alone`, one after the other in the whole browser, and whoever deletes looks at the device once it has the lock: it leaves a session alone that is not the one it began with. A browser without Web Locks has only that look.
- **Nothing waits for somebody else.** When somebody else has signed in, when the person has signed out, or when the kept changes were deleted on the sign-in page, a tab starts again at once, also one that is waiting, because nothing of one person is shown to the next. If the same person signs in again while a tab waits, it goes on waiting, and starts again as that session when its wait is over. A tab that does not wait and hears that the same person is signed in again, such as one that the browser had put aside and that hears of the end and of the new session at once, starts again only when it has stored what it holds, `whenSaved()`: nothing presses, and the page load would lose the change without the browser's question. Do not close the sync of a tab, with `closeWorkspaceSync`, for a session that ended by itself before this wait is over: that is what loses the changes.
- **What signing out would lose is counted in both workspaces.** `countUnsynced` goes through every copy of the person. The changes that a tab could not store are in no copy: the stores ask each other for them on a channel that reaches every tab of the person and both workspaces, `pigy/<user ID>`, which is why `workspace-sync.ts` gives a store two `BroadcastChannel`s. Signing out deletes the copies of both workspaces and the choice: the device's, and that of the tab. The other tabs keep theirs where the tab that signs out cannot reach it, so each forgets its own before it starts again, in the `storage` handler of `lib/session.ts`. The sign-in page forgets what it finds too, and a tab does not always come by it: it can start again when the same person has signed in again in another tab.

## The service worker

A build of the web app installs as an app and starts without a connection. `PLAN.md` section 13 is the design: what the service worker keeps, how a new version takes over, what a device holds. What to know when working on it:

- **What it is made of.** `apps/web/src/sw/sw.ts` listens to the browser and does nothing else. `precache.ts` is what the worker does: it keeps the files of its build and answers for them. It takes `caches` and `fetch` as parameters, so that its tests need no browser. `push.ts` is what it does about push messages, in the same way: `shownFor` makes the words of a notification from a message, and `clicked` takes whoever presses one to the screen that it is about. `worker-paths.ts` says which paths are the Worker's, `messages.ts` has what a page says to the worker, and `build.ts` what the build tells it.
- **How it is built.** `apps/web/service-worker-plugin.ts` builds `sw.ts` into `/sw.js` once the web app is built, as one file with no imports, because a service worker is not loaded as a module. The build writes two things into it: the files that it has, and the patterns of `assets.run_worker_first`, which `vite.config.ts` reads from `wrangler.jsonc`. `pnpm dev` builds nothing, so it has no service worker: `lib/service-worker.ts` registers one only in a build. `src/sw` is type-checked apart from the app, with `tsconfig.sw.json`: where it runs there is no page, so it has no `window` and no `document`.
- **What it must never do.** Answer for a path of the Worker. Keep anything that is somebody's, such as an answer of the API or synced data: the local copy in IndexedDB is the only place where data of a workspace is on a device. Take over by itself: the pages that are open run another build.
- **How a new version takes over.** `lib/service-worker.ts` has the rules, and the comment at its top is the place to read them. A new worker is installed next to the running one and waits: for the last window to be closed, for a page that starts, which asks it to take over before it shows anything, or for "Reload to update", which is such a start. The worker that takes over deletes the files of the build before it, so one rule stands behind the rest: no window goes on under a worker of another build. Three things keep it:
  - Every window that is open loads itself again when a new worker has taken over, once it holds no change that is not stored, in either workspace. That is `whenSaved()` of `sync/workspace-sync.ts`, and anything that loads a page again for a new version waits for it. It is over at once unless the device fails to store a change, and then the window stays.
  - So that no window has to stay like that, a window that holds changes which it could not store, in either workspace, holds the Web Lock `pigy/unsaved`, and a page that starts while anybody holds it does not ask the waiting worker to take over: it starts as the version it is, whose files are there. The new version waits on, for the last window to close or for a start after the changes are stored. The app has no screen before that is decided, so the question to the browser is given three seconds: `mayTakeOver` decides against the take-over without an answer, and for it when the browser fails to answer, as where there are no Web Locks. "Reload to update" would be such a start and bring the old version back, so `reloadToUpdate` does not reload while the lock is held: `useReloadToUpdate` in `lib/reload-to-update.ts`, which every button for it uses, says in a notice that another window is in the way. What is left is a write that fails in the instant after a page that starts has looked.
  - A page that no worker answered for, because it was loaded before the first worker was installed or with a reload that goes past the worker, is taken on by the next worker that is activated. If that worker does not keep the script that the page was started from, it is of another build, and the page loads itself again.
- **What must not change between versions.** A page of one version talks to the worker and the windows of another, so four names are contracts: the message `activateMessage` in `sw/messages.ts`, the prefix `pigy-app-` of the caches in `sw/precache.ts`, and the names of two locks, `unsavedLock` in `sync/workspace-sync.ts` and `sessionLock` in `lib/session.ts`, under which a session is taken on and cleaned up after. Each says so where it is defined. The lock is also held by a window that waits for what it has not stored after its session has ended, for the whole wait: a new version does not take over then either, for the same reason.
- **What it keeps.** Every file of the build, those of `apps/web/public` included, without anybody listing them. A second HTML page fails the build: the service worker has one page, the app shell. A file that the app loads from somewhere other than its own build is not kept, and is missing offline.
- **A new path of the Worker.** A route that a browser navigates to goes under a prefix that `assets.run_worker_first` in `wrangler.jsonc` has: `/api/`, `/connect/`, `/sim/` or `/sync/`. The list has `/assets/*` too, which is no place for a route: the Worker passes the files there on and answers a path without a file with a 404, `src/assets.ts`. The service worker answers for a file of its build before it asks the list, so the files under `/assets/` are kept on the device like the others. The list is built into each `sw.js`, and a device keeps the service worker that it has until the app is next started there. Until then a navigation to a prefix that a deploy has added gets the app shell from the worker of the release before, on that device. So a new prefix takes a changeover: first a release whose service worker knows the prefix, and only when the devices have taken that one over, whatever sends a browser there. The prefix itself goes into `assets.run_worker_first` and nowhere else, and `e2e/tests/offline.spec.ts` tests one path for every pattern in that list, with the service worker of the same build.
- **Push messages.** The Worker sends JSON of the form `pushMessageSchema` of `packages/core`, which holds IDs and no words, and the service worker makes the words. The two are released together but not taken over together: a device runs the service worker that it has until the app is next started there. So a new kind of message is shown in general words by the workers that do not know it, which `shownFor` sees to and its tests show, and a change of the form takes a new `v`. Something is always shown: a browser takes the subscription away from a site whose messages show nothing. A field that is added to the form is optional, and a worker that does not know it does without, as with `expiresAt` of a reminder.
- **A notification that is pressed.** `clicked` of `sw/push.ts` tells a window of the app where to go, with `navigateMessage` and a port, and the window answers on the port with `navigatedMessage`: `onNotificationPressed` of `lib/service-worker.ts`. Without an answer the worker opens a window. A browser gives a worker about a second after the press to bring a window to the front or to open one, so all of it takes `answerWithinMs`, 400 milliseconds, from the press: a hidden window is brought to the front first and then told, a visible one is told first, and an `openWindow` that the browser refuses is caught. Do not add a wait to `clicked` without taking it out of that time. A window at a path of the Worker is no window of the app, by `worker-paths.ts`. What the worker opens and where a window goes is one rule, `appPath` of `@pigy/core`, which the worker imports from `@pigy/core/return-to`: the entry point of the package would put all of it, Zod included, into `sw.js`.
- **A push subscription that the browser replaces** is told to the worker alone. It passes that on to the windows, `subscriptionChangedMessage`, and decides nothing: a window knows who is signed in and whether they turned notifications on.
- **What is shared to pigy** needs nothing of the service worker. The share target of the manifest is `/share`, an address of the app, which gets the app shell like any screen. Any website can send a browser to that address, so opening it stores nothing: "Rules" has it.
- A request that the service worker is to answer in a new way is decided in `precache.ts`, next to the others, with a test.
- **Trying it by hand.** `pnpm preview:e2e`, then http://localhost:4173 in Chrome, or the port of `PIGY_E2E_PORT`. Sign in, and the service worker is installed: DevTools shows it under Application. Chrome offers to install the app in its address bar, and Settings do once Chrome has told the page that it can be installed, which takes half a minute of use. For a start without a connection, tick "Offline" under Network and reload. For a new version, stop the server, change something in `apps/web/src`, and run `pnpm --filter @pigy/web build:e2e && pnpm --filter @pigy/web preview:e2e`, which keeps the database. A window that was open says in Settings that a new version is ready once it has come back to the front, and the next window that is opened is the new version. On a phone it cannot be tried before phase 11: installing takes HTTPS, or `localhost` on the device itself.

## The content security policy

Every answer says what a browser may do with it. `PLAN.md` section 16 is the design. What to know when working on it:

- **Two places.** Cloudflare serves the files of the web app without the Worker, with the headers of `apps/web/public/_headers`: the rule for `/*` is the policy of the app shell, and so of every screen. The Worker gives its own answers theirs, in the middleware `securityHeaders` of `apps/worker/src/security-headers.ts`. The headers that both send, such as `Referrer-Policy`, are written in both, and `e2e/tests/security-headers.spec.ts` compares them.
- **Not in `pnpm dev`.** The dev server has no `_headers` and adds scripts of its own to the page. What the policy refuses shows in a build: `pnpm preview:e2e`, where the console of the browser names it, and `pnpm e2e`, where every test fails that met it.
- **The hashes are written by the build.** `_headers` has two placeholders, `{{inline-scripts}}` and `{{injected-styles}}`, and `security-headers-plugin.ts` puts the hashes there: of the one inline script of `index.html`, and of the style sheet that the notice library adds to the page. The build fails if `index.html` has another inline script, a `<style>`, a `style` attribute or an inline event handler, and if the library has changed how it adds its styles.
- **A library that adds a `<style>` element to the page**, as sonner does, shows as `style-src-elem refused inline` in the end-to-end tests. If its text is the same every time, the plugin reads it from the installed package and allows it by its hash, as `sonnerStyles` does. If it is not, the library has to be given a way around it, or does not fit: do not allow inline styles for it. A style that React sets through the `style` prop is set through the style object of the element, which no policy is asked about.
- **A library that uses `eval` or `new Function`** shows as `script-src refused eval`. Zod did, to compile its schemas: `apps/web/zod-without-eval.ts` tells it not to, and `vite.config.ts` puts that file in the place of `zod` for every build, because the schemas of `@pigy/core` are made while their modules load, before any code of the app has run.
- **Something that the app loads from elsewhere** has to be named in the policy of `_headers`, by the directive for its kind. Think first: the service worker keeps only the files of the build, so it would be missing offline.
- **A page that the Worker answers with** gets a policy by itself: no script, and the `<style>` elements of its head by their hashes, which is what the pages of the simulations are made for. A page that needs more sets `Content-Security-Policy` on its answer, and the middleware leaves it alone: the narrowest that works, with a script from a file under a path of the Worker, or a nonce that is made for the one answer, and never `'unsafe-inline'`. Everything that is no page gets `default-src 'none'`.
- **A file that the Worker passes on**, as `src/assets.ts` does, is left as Cloudflare answered it: the route sets `passedOn`.
- **A form** of a page of the Worker is sent to pigy alone, `form-action 'self'`, and a browser asks that of the redirect that answers the form as well. A form of the app is never sent by the browser, `form-action 'none'`: it has a handler that keeps the browser from it.

## Rules

- Tests never reach a real network host. External services are simulated.
- No tautological tests. When a test step or assertion is not obvious, add a comment saying why it is there.
- Code that talks to external services takes `fetch` and the clock as parameters, typed `Fetch` and `Clock` from `@pigy/core`. It never uses the globals. In the Worker both come from `createApp` in `src/app.ts`. The sync client takes its timers the same way, typed `Schedule`, so that its tests wait for nothing.
- A `Fetch` fails with a `TypeError` when no answer comes, as the Fetch standard has it, and with nothing else then. `send` of `@pigy/providers` takes a `TypeError`, and a request whose time is up, for a network that is out of reach, and asks to try again. Whatever else a `fetch` throws is passed on as it is and ends in the log as a failure of pigy's: a check in the simulated world of a sandbox that refuses, a bug in a simulator. The Workers runtime fails with a plain `Error` when a connection is lost, so `outboundFetch` in `apps/worker/src/outbound.ts` turns what the runtime's `fetch` throws into a `TypeError`. A simulator throws a `TypeError` for a host that is not its own and for an answer that a fault loses, and for nothing else. The way into the simulated world of a sandbox can break like a connection too: the runtime fails a call into a Durable Object with an error that it marks `retryable` or `overloaded` when the trouble is its own, and `worldFetch` in `apps/worker/src/sim/world.ts` turns that into a `TypeError`. What the object itself throws has neither mark and stays a failure of pigy's. So a method of an adapter can fail with something that is no `ProviderError`: the top of `packages/providers/src/provider.ts` says what a caller does with it.
- The page of a link is read by `fetchLinkCard` of `@pigy/providers/card` and in no other way, with the `fetch` that `reachOf` gives the workspace: the simulated web for a sandbox. Nothing of a page is run or put into a page as markup. What it says of itself is text of a bounded length, and a failure to read it fails nothing: the link has no card. The page is looked through by `readPage` of the same file, once and forward, in work that is bounded by its length whatever it is: no timer interrupts the looking, so nothing is added there that searches the rest of a page again, or that changes the text and then goes by places in it, as lowering it does. `card.test.ts` has the pages that are made to make it work, and counts. The browser of a person asks the page of a link for nothing, a picture included.
- What is a link, a mention or a hashtag is decided by `detectEntities` of `@pigy/core` and nowhere else: the editor marks with it and the adapters mark up with it. A simulator finds them in code of its own, and the conformance suite compares the two.
- A network is reached through its adapter in `packages/providers` and in no other way. What an adapter hands out to be stored, credentials above all, is opaque: store it, hand it back, never read it.
- In the Worker, an adapter is made by `providerOf` in `src/network/providers.ts` and in no other way. It gives the adapter the `fetch` of its workspace: the simulated world of a sandbox, the app's own `fetch` for a live workspace. Nothing else may choose, and nothing in a request may influence it.
- Secrets that are not pigy's own are sealed with `src/vault.ts` before they are stored: the credentials of a channel, a registration with a network, what a connection in progress needs. They are opened only where an adapter is called with them. For the credentials of a channel that is `openCredentials` of `src/channels/credentials.ts` and nothing else: no other code calls the vault for them. They never go into a log, an error, a sync message or an answer, and neither does an error that could hold one: log the message of a `ProviderError` or a `VaultError`, which hold none. An error of the database does hold some: Drizzle puts the values of a statement that failed into its error, and a sealed registration, the hash of a session or the `state` of a callback can be among them. `handleError` logs what a route lets through without them, and so does everything else that logs: `log` of `src/log.ts` passes every error through `loggable`.
- What a run of a workflow is started with, and what each of its steps returns, is stored by the platform, where everybody with access to the account reads it. Neither holds a secret, sealed or not: a step asks the workspace for the credentials of its channel, opens them where it calls the adapter, and returns nothing of them. The progress of an adapter is made for this: it holds no secret by contract.
- A step of the publishing workflow that talks to a network does not fail as a step. What goes wrong in it is what it returns: `tried` in `src/publish/workflow.ts`. An error that is thrown out of a step reaches the workflow as a message without its class, and the platform would run the step again on a schedule of its own, whatever the network said. The workflow catches nothing that it has not thrown itself: what the platform throws into a run, to stop it or because it has given up on a step, is thrown on, and the object of the workspace ends such a delivery. That has no exception. The step `cards`, which reads the pages of links and without which a delivery goes on, is made so that it does not fail, and nothing is caught around it either: `readCards` of `src/publish/cards.ts` takes a page that cannot be read for a link without a card, logs what goes wrong in the reading, and is over within a time of its own, well below the step's. A step that a delivery can do without is made like that one, and never by a catch around it that tells what the platform threw by the words of an error: `PLAN.md` section 6, "Links, mentions and hashtags".
- An adapter that says `repeatsSafely` is false, as LinkedIn's, can neither look for what it has sent nor send a request that is carried out once. Its `publishStep` is called through `sendingOnce` of `src/publish/workflow.ts` and in no other way: the workspace notes that the step begins before the adapter is called, and a second run of the same step, by the platform or by somebody who restarts the run, does not call it and ends the delivery as `uncertain`. So does a step that finds no note for a delivery that is 29 days old or older: the workspace keeps a note for 30 days, and one may have been there. A step whose call to the workspace fails repeats it with the same mark before it gives up. `PLAN.md` section 8 has the design, at its end.
- The time of a queued post is computed by the mutators and by nothing else: `requeue` in `packages/core/src/sync/mutators.ts`, which every mutator runs that changes the queue, the slots, the time zone or the pause. A screen reads `dueAt` and computes none, and neither does the Worker. A mutator that computes with a time zone does so with `packages/core/src/schedule/zone.ts`, which is the same code in the browser and in the Worker.
- A scheduled post goes out through the mutator `post.due`, which the object of the workspace runs, and in no other way: it does what `post.publish` does, so a due post is a delivery like every other from there. The alarm of a workspace is set in two places of `src/workspace/object.ts` and nowhere else: by `#setNextAlarm` after a change, and by `alarm` when it has looked. Both set it to the moment that `#nextLookIn` names, which is the one list of what the alarm is for: something new that the object is to do by itself goes there, with its time, and not into a `setAlarm` of its own. A change never puts the alarm off. The alarm never comes back at once for something that it has just tried and that failed: that would be a loop. And it fails, for the runtime to run it again, only when it could not set the next one. `PLAN.md` section 9 has why the runtime is asked what the alarm is set to, and the object keeps no record of it.
- A scheduled post is deleted in two steps, and its Undo is never a copy: `post.trash` puts it aside, `post.restore` takes that back, and `post.delete` with `ifTrashed` deletes it when the Undo is no longer offered. `putAside`, `restore` and `deleteForGood` of `apps/web/src/lib/queue.ts` are the three, and the object of the workspace deletes a post that was put aside a day ago, `pruneTrashed` of `src/workspace/store.ts`. A post that is put aside is as good as gone: whatever reads the scheduled posts leaves it out, on the server and on a screen, as `inQueue` and `scheduledCount` of the mutators do and `isScheduled` of `lib/queue.ts`. A device that is behind the server would otherwise publish a post twice. `PLAN.md` section 9 has the order of events.
- A mutator gives the posts of the queue their times once, with one `requeue`, however many posts it changes: `channel.disconnect` shows how, and a test of `packages/core/src/sync/schedule.test.ts` counts. `queuePosition` says the order of the queue and nothing else: a screen that shows a place counts it, as `selectQueue` does.
- A network is published to by the publishing workflow and in no other way, and a delivery begins in `startDeliveries` of `src/workspace/store.ts` and nowhere else: that is what keeps the deliveries to one account one after the other, which every adapter counts on.
- Nothing that crosses into a Durable Object or out of it is a `Request`, a `Response` or a stream. Pass plain data, read whole. A body that crosses as a stream keeps the call open until somebody has read it, and code that refuses a request early does not read it.
- What a network or a person says is untrusted. A host that a person names is validated before a request goes to it. What a network puts into an error reaches a message only through `quotable` of `@pigy/providers`, which takes the secrets of the request out.
- Validate data at boundaries with Zod schemas from `packages/core`. Share types, do not duplicate them.
- The synced data of a workspace changes only through mutators from `packages/core`, run by the workspace's Durable Object. No other code writes to a synced table.
- A screen reads synced data from the local copy and changes it with a mutator. It does not fetch synced data, does not wait for the server and has no loading state for it. Only what is not synced, such as the allowlist, goes through `lib/api.ts`. So does what a client may not change by itself, which is connecting and disconnecting an account: it needs a connection, and the screen says so without one. The list of channels is still read from the local copy.
- A screen takes the workspace from the route context, `Route.useRouteContext().workspace`, and keeps it nowhere else. Whatever it shows of a workspace has to go when the workspace changes: see "Live and sandbox in the app".
- What an address says is the word of whoever made it. The screen that `/channels?connect=…` leads to shows a text of its own for each outcome and names an account only from the row of its channel.
- The app starts without a connection, so nothing on the way to the first screen may wait for the server. Where it has to, because the device does not know who is signed in, and on the sign-in page, the question is given ten seconds: `answeredInTime` of `lib/api.ts`, which makes a request that is never answered one that got no answer. A device that holds a session which is over asks in `loadSession` and again on the sign-in page that it is sent to: when the first question got no answer, the page takes that for its own, `serverJustSilent`, so that it is one wait. The check of a session in the background goes through it too, or a question that stays open would be the last one of its window. It takes its timer as a parameter, for its tests. A screen that needs the server says so when it cannot reach it, and offers to try again, as Settings → About does. The two pages that stand in for the app when it cannot start, the one that says that pigy cannot reach its server and the sign-in page, also try again by themselves when the browser says that the connection is back: `useOnline` in `lib/online.ts`.
- The service worker keeps the files of the app and nothing else. What the API answers and what is synced never go into a cache.
- `index.html` has one inline script, which sets the theme before the first paint. Nothing else is inline, in `index.html` or in what the app adds to a page: the content security policy allows that script by its hash, and every other one by where it comes from. The build computes the hash and writes it into `_headers`, and fails for a second inline script. Never write a hash into `_headers` by hand, and never add `'unsafe-inline'` or `'unsafe-eval'` to a policy: see "The content security policy" below for what to do about a library that needs one.
- The Worker writes to its log with `log` of `src/log.ts` and in no other way: Biome refuses `console` in `apps/worker/src`. A line has a kind from `LogKind`, a message in words, and the IDs of what it is about as fields, not in the message: the workspace, the channel, the target. It never has a secret, the text of a post, the name or the address of a person or an account, or the query of an address. The message of a `ProviderError` or a `VaultError` holds no secret and may be part of the message. Any other error is handed to `log` as the error, which passes it through `loggable`.
- `SYNC.md` is the contract with the clients. Change it in the same change as the code. Raise `syncProtocolVersion` when the messages or their meaning change and `syncSchemaVersion` when the synced tables or the mutators do: a client that speaks another version is turned away until it has updated itself.
- The inbox is told through the mutators, and the devices through the inbox: a push message is queued by `WorkspaceStore` for a notification that a mutator has made, and for nothing else. Do not send one from a route or a workflow. Whether a post is told of is decided in `announce` of `packages/core/src/sync/mutators.ts`, when the post leaves `sending`, and nowhere else: a mutator that ends a delivery calls `settle`. It goes by `updatedAt` of the post, which is when the post last began to be sent, so no mutator writes that for a post that is `sending`: `schedule.test.ts` of `packages/core` holds the mutators of scheduling to it. That a scheduled post is held is told by `takeUp`, which holds it, and what the inbox says of a post goes through `forgetNoticeOfPost` wherever the post is released, put aside or deleted. A mutator that reads or dismisses a notification names it with the `createdAt` that the device saw.
- Sending push messages never keeps the alarm of a workspace from its deliveries: `#sendPushes` of `src/workspace/object.ts`. What is added to the alarm after the deliveries is bounded, or stands aside for them in the same way. What a push message holds is IDs: no text of a post and no name of an account, which would show on a lock screen.
- The address of a push service is named by a browser. It goes through `pushEndpoint` of `src/push/subscriptions.ts` before it is stored and before anything is sent to it, which lets through only the hosts of the push services in `pushServiceHosts`: a browser whose push service is not there has to be added to that list, and nothing else widens it.
- An address of the app that anybody can make stores nothing by being opened. `/share` shows what came and asks, and what it shows is read from the address as the browser has it, `window.location.search`: the router reads the values of a query as JSON. What was shared to somebody who is signed out does not go through the sign-in in `returnTo`, which the Worker cuts off at 1,000 characters: the tab keeps it, and the way back is `/share` alone. The endpoint and the keys of a subscription never go into a log, an error or an answer: log the host of a push service and nothing else of it.
- Nothing that runs in a Durable Object leaves a timer behind. The runtime keeps an object busy for as long as one is pending, so `AbortSignal.timeout` does not belong there: use a timer that is called off when the work is done, as `sendPush` does.
- The public API is called with a key and with nothing else. No route under `/api/v1` reads the session cookie, and none answers with a CORS header: a page must not be able to call the API as the person who looks at it. The routes that manage keys are the other way round: the session, never a key.
- A key of the API reaches the workspace that it belongs to. A route under `/api/v1` takes the workspace from the key, `c.var.api.workspace`, and nothing in a request names one.
- The public API writes with the mutators and in no other way, through `carryOut` of `apps/worker/src/workspace/api.ts`, where a call is one change. What is to go out is checked there with `publishable`, by the rules that the editor of the app has in `compose`: change the two together.
- An API key is in the one answer that made it and nowhere else: not in a log, not in an error, not in D1, which has a hash of its secret. What names a key in a log or to the rate limiter is its ID.
- Wherever the sessions of an account are ended because Google no longer says that its stored address is its own, its API keys are revoked in the same batch: `revokeAccessAtRefusedSignIn` and `revokeAccessOfOtherAccountsWith` of `src/auth/session.ts`. So are the keys of the accounts that are stored with an address which is removed from the allowlist, in the batch of the removal, with `revokeKeysOf`. A key is matched against the stored address of its owner, which stays stored, so a new way for an identity to end that deletes sessions and leaves the keys lets them go on publishing.
- Nothing that the API keeps or answers grows with what is in a workspace without a bound. Under an `Idempotency-Key` it keeps a status and what to read, and builds the body of a repeat anew: a body that is kept can be larger than a row of the object's database takes, and is parsed later with the shape of another day. An answer carries `maxApiAnswerTextLength` characters of texts at most: a new field that repeats a text, or a new list, is counted against it in `postResource` and `listPosts` of `src/workspace/api.ts`. What an answer leaves out for it, it says that it leaves out, with a field of its own and never with a null that also means something else, and a route hands it out by itself: `textOmitted` of a target, and `GET /posts/{id}/targets/{channelId}`.
- A time goes into an answer of the API through `apiTime` of `@pigy/core/api` and in no other way: a row can hold a time after the year 9999, which a date writes in a form that the answers do not promise.
- A bug of a mutator is no refusal of the API. `carryOut` throws for `internal_error`, so that the call has not happened and nothing is kept under its key.
- No secrets in the repository. Local secrets go in `apps/worker/.dev.vars`, which is git-ignored.
- `PLAN.md` is the design. If an implementation must deviate, update `PLAN.md` in the same change and say why.

## How to

**Add a screen.** Create `apps/web/src/routes/_app/<name>.tsx` with `createFileRoute` and wrap the content in `<Page title="…">`. `actions` puts buttons next to the title, and `fill` hands the screen the whole body to lay out, as the drafts screen does for its two panes. `heading` hands out the title and lets it take the focus from code: that is where a screen sends the keyboard when what had the focus is gone and nothing else can take it, as the Channels screen does after a disconnect that ends without a connection. Everything under `_app` needs a session: `_app.tsx` learns who is signed in before anything renders and puts it into the route context, `Route.useRouteContext().me`, with the workspace that is open, `workspace`, which is the live one or the sandbox. A screen is made anew when the person changes workspaces, so it holds nothing of the other one. A notice that it puts on screen with `toast` outlives the screen and leaves with the workspace, by itself, unless it is made one of the person's: see "Live and sandbox in the app". If it keeps something of a workspace in its address, as the drafts screen keeps the open draft, nothing has to be done: changing workspaces drops the search of the address. On a device that has been signed in before, that is the word of the device, which the server is asked about in the background: see `lib/session.ts`. A screen for people who are not signed in goes next to `sign-in.tsx` and uses `<PublicPage>`. The dev server and the build regenerate `src/routeTree.gen.ts`: commit it, never edit it. Add the route to `allNavItems` in `src/components/app-shell.tsx` if it belongs in the navigation, and to `screens` in `src/components/command-palette.tsx`. A screen that only one of the two workspaces has, as the Simulator is the sandbox's, is named in `hasScreen` of `lib/workspace.ts`, the one place that says which workspace has which screen: the navigation and the palette leave it out for the other workspace by it, `useSwitchWorkspace` goes to the drafts when the workspace that is switched to does not have the screen that is open, and its route renders a screen that says that there is nothing at the address there, from the workspace in the route context: `routes/_app/simulator.tsx`. The phone has room for six items in its bar.

**Ask the server for what is not synced.** Write the request in `lib/api.ts`, with its schema from `packages/core`, and read it in the screen with `useFetched(request)` of `lib/fetched.ts`, with a `request` declared outside the component. The schema of an answer is a `z.object`, never a `z.strictObject`, at every depth: a device runs the app that it has until it is next started, so the client of one release reads the answers of the next, and a field that it does not know must not make it refuse the answer. "Add an API route" has the rule. It has a loading state and a failure, which synced data has not: say both, with `failureMessage`, and offer to try again, with `refresh`. A screen that shows the world of a sandbox asks again when something that changes the world has happened, which the synced tables say: `useWorldChanges(refresh, loading)` of `lib/sandbox-world.ts`, which the feeds and the failure panel use, asks again when a delivery moves on, by `selectDeliveries`, and when the connection or the person is back. While a delivery is being sent, by `selectSending`, it also asks every few seconds, on a timer that `page.clock` moves: a network that asks to be tried again changes the world long before the workspace says anything. A refresh that fails while an answer is on screen keeps the answer and says that it is from before, with `RefreshFailure` of `components/refresh-failure.tsx`. A request that changes what was fetched answers with what it left, and the screen makes it with `change` of `useFetched`, which shows the answer and keeps reads and changes apart: a read that is asked for while a change is on its way is made after its answer, so that an older answer never takes the place of a newer one. Two changes whose answers arrive the other way round would still leave the older answer on screen, so a screen makes one at a time and disables what would start another, as the failure panel does. Nothing that is fetched is kept anywhere but in the screen, so it goes with the screen when the workspace changes.

**Read synced data in a component.** `useSynced(select)` from `@/sync/react` hands `select` the synced tables, each a `Map` from ID to row, and returns what it returns. The tables are what to show: the rows of the server with the changes of this device that are not confirmed yet. The component renders again when a row changes. Write `select` as a function of its own in `src/lib`, like `selectDrafts` in `lib/drafts.ts`: it has to be the same function on every render, and it is where sorting and joining belong. A row that has not changed is the same object in every view, so a `select` that makes items for a list can hand out the item it made of that row before, as `draftOf` does there. A row component wrapped in `memo` then renders only when its item has changed, which is what keeps typing cheap in a long list. There is nothing to wait for and nothing to fail, so no loading or error state. In an event handler, `useSyncedNow()` returns a function that reads the tables without making the component render. `useSyncState()` says how sync is getting on, for the indicator in the shell: the connection, how many changes the server has not confirmed, and how many of them the device could not store. Whatever warns before work is discarded has to count the last ones too, in every tab: they are in no database. `store.unsavedInAllTabs()` asks the other tabs for theirs, as the sign-out in `components/user-menu.tsx` does. `unsavedInTab()` of `sync/workspace-sync.ts` counts those of this tab in both workspaces, which is what decides whether the browser asks before the page goes.

**Change synced data from a component.** `const mutate = useMutate()`, then `mutate("part.setText", { id, text })`: the name of a mutator and its arguments, checked by the compiler. It returns at once and the change is on screen, in every tab. Make up the ID of a new row with `uuidv7(new Date())`. There is no result to wait for: if the server refuses the mutation, the change is taken back and `Rejections` in `components/rejections.tsx` tells the person. A field that is typed into can call `mutate` on every keystroke, as the editor of a draft does.

**Add a keyboard shortcut or a command.** `useShortcuts` in `src/lib/keyboard.ts` hands a screen the key presses that are not typing and not meant for a dialog or a menu. It hands out none while a dialog of `components/ui` is open, wherever the key press comes from: a button of a dialog that is disabled while its request is on its way gives the focus up, and the next key press comes from the page. A key that is handled with `useKeyDown` instead asks `isBusy` of the same file, which says both. A shortcut that works on every screen, and every command of the palette, goes into `components/command-palette.tsx`. The palette lists a screen whose name is typed in full before everything else, `namedScreen` of `lib/palette.ts`: a command may have the name of a screen in its own, as "Pause the queue" has, and Enter after "queue" still leads to the screen. It is written as a group of its own at the top for that. The palette library sorts what matches within a group and leaves the groups in the order that they are written in, so a command of an earlier group comes before a better match of a later one. The palette does not open over such a dialog either, so a command never runs behind a question that is open. A request whose answer has to reach the person even if they leave the screen meanwhile says it in a notice then, as the disconnect in `routes/_app/channels.tsx` does. That notice is the person's, with `keepOverSwitch`: it stays when they change workspaces, and names the workspace that it is about. Show the keys where the thing is done: `Kbd` in a button, a tooltip or the palette. A key handler of a text field returns at once while an input method composes a character, `event.isComposing` or the `keyCode` 229, as the fields of the parts of a draft do: the arrows, ⌫, Enter and Escape are the input method's then. And a button that leaves the page when it is pressed, as "Customize for …" does and every button of a notice, takes the keyboard with it to the page, where the next key is a shortcut of the screen: send the keyboard somewhere, with `takeFocus` of the same file, which also holds against the notice library, which hands the keyboard back to where it was before the notice.

**Add a shadcn/ui component.** Run `pnpm --filter @pigy/web exec shadcn add <name>`, then `pnpm format` from the root. This runs the `shadcn` version that `apps/web` depends on, the same one whose CSS its styles import. Components land in `apps/web/src/components/ui`. Theme tokens are in `apps/web/src/styles.css`. If the command asks whether to overwrite a component that exists, say no. The components are written for Next.js: delete a `"use client"` line, and replace `next-themes` with `useTheme` from `components/theme-provider.tsx` and remove the package, as `ui/sonner.tsx` shows.

**Add an API route.** Add it to a group of routes under `/api/` in `apps/worker/src`, or add a group and mount it in `app.ts`. Put the request and response schemas in `packages/core` and parse with them on both sides: `parseJsonBody` in `src/errors.ts` does it for a request body. The schema of a request is strict, so that a mistake of a client is told. The schema of an answer is not: it is a `z.object`, at every depth, which leaves out a field that it does not know and refuses nothing for it. After a deploy the windows that are open, and an installed app until it is next started, are the app of the release before, and they read the answers of the new Worker: a field that is added to an answer has to pass them by, and `packages/core/src/answers.test.ts` holds the schemas to that. Adding a field is then all that it takes. Taking a field away, or changing what one means, still breaks the app of the release before, and takes a new route or a parameter that the new app asks with. The feed of a sandbox has such a parameter, `sandboxFeedMarks`, from the time before this rule: its posts got two fields in phase 4b, which the app of the release before refused. To refuse a request, throw Hono's `HTTPException` with the status and a message for the client. It becomes an error response in the shape of `errorResponseSchema`, with the error name that `PLAN.md` section 12 gives the status. When a 400 is about one field of the request, throw `InvalidField` of `src/errors.ts` instead: the answer then names the field in `field`, for a form to show the message next to the input. `parseJsonBody` does so for a body that does not parse. Any other exception becomes a JSON 500 that says nothing about it, and is logged with the method and the path of the request, without the values of a database statement that failed. Work that must go to its end even if the client leaves, because nothing can do it a second time, is handed to `c.executionCtx.waitUntil` before the route waits for it: the runtime drops what is left of a request whose client is gone. The route that disconnects a channel is the example. Guard a route with `requireUser`, and `requireAdmin` after it, from `src/auth/guards.ts`: the first also refuses requests that change something and do not come from pigy's own pages. In the web app, call the route through `request` in `apps/web/src/lib/api.ts`. Only the paths that `assets.run_worker_first` in `wrangler.jsonc` lists reach the Worker: `/api/*`, `/connect/*`, `/sim/*` and `/sync/*`, and `/assets/*`, which is for the files of the build alone. Every other path is a static asset or the app shell, so a new prefix must be added to that list. An answer gets its security headers by itself, and a policy that allows a browser nothing: a route that answers with a page reads "The content security policy" below. The service worker of a build has the same list and leaves those paths to the network, but a device runs the service worker of the release before until the app is next started there. So put a route that a browser navigates to under a prefix that exists: "A new path of the Worker" under "The service worker" says what a new prefix takes.

**Add a route to the public API.** Put the schemas of its request and its answer into `packages/core/src/api/v1.ts`, with `named` for one that the document is to list by name and `.describe()` for what a field needs said, and add the route to `apiOperations`: method, path, scope, schemas and the status of a success. The compiler then asks for its handler in `apps/worker/src/api/routes.ts`: in `workspaceRoutes` if it reads or writes the workspace, where it returns an `ApiCall`, or in `ownRoutes`. Add the call to `ApiCall` and to `carryOut` of `apps/worker/src/workspace/api.ts`, which makes every change with `mutate` and refuses by throwing `ApiRefusal`, with the field that the refusal is about if it is about one. A route that writes and whose answer is neither a post nor the posting schedule also says in `keptOf` of that file what a repeat of it reads: nothing is kept of a body. Nothing else: the OpenAPI document and the docs page are made from the list, every route that is not a GET takes `Idempotency-Key` by itself, and the tests that compare the routes with the document and hold every route to its scope go through the list too. Test the route in both environments where what it does differs between them, as `apps/worker/test/api-posts.test.ts` does.

**Change the icon.** Edit `assets/icon.svg` and run `pnpm icons`. It draws the icons of the installed app into `apps/web/public/icons` and copies the icon itself to `apps/web/public/icon.svg`, with the Chromium of the end-to-end tests, which has to be installed. Commit what it writes. The sizes and the shapes are in `e2e/scripts/generate-icons.mjs`, the manifest that names them is `apps/web/public/manifest.webmanifest`, and `e2e/tests/install.spec.ts` checks that the two agree. The colours of the app's two backgrounds are in three places that the same test compares: `--background` in `styles.css`, the `theme-color` tag in `index.html`, and the manifest, which has the light one.

**Change the database schema.** There are two databases. Never edit a migration of either that is on `main`.

- D1 holds sign-in and what is global. Edit `apps/worker/src/db/schema.ts`, run `pnpm --filter @pigy/worker db:generate --name <what_changed>` and commit the files it adds to `apps/worker/migrations`. The migrations are applied by `pnpm dev`, `pnpm preview` and `pnpm preview:e2e` when they start, and by `test/setup.ts` before every Worker test. A deploy applies them before it replaces the Worker, so the code of the release before runs on the new schema for a moment, and for good if the deploy then fails. A migration therefore only adds what that code can ignore: a table, or a column that is nullable or has a default. What a release no longer needs is dropped by a later release, and a column is never renamed: it is added, filled and, a release later, dropped.
- Every workspace has a SQLite database in its Durable Object. Edit `apps/worker/src/workspace/schema.ts`, run `pnpm --filter @pigy/worker workspace:generate --name <what_changed>` and commit what it adds and changes in `apps/worker/src/workspace/migrations`. That includes `migrations.js`, which imports the SQL files and is how they get into the Worker. Nothing applies these migrations from outside: each object applies them to its own database when it starts, so after a deploy a workspace is migrated the next time it is used. A migration therefore has to work on a database of any age, and the code must not assume that all workspaces change at once.

**Add a synced table**, one that clients hold a copy of.

1. Describe its rows in `packages/core/src/sync/tables.ts`: a strict Zod schema with an `id`, added to `rowSchemas`. Add `putSchema("<table>")` to `changeSchema` in `protocol.ts`.
2. Add the table to `apps/worker/src/workspace/schema.ts` and generate the migration. No "on delete cascade" and no triggers: a row that the database changes by itself is a change that no client hears of.
3. List the table and its synced columns in `synced` in `apps/worker/src/workspace/synced.ts`. The compiler compares the list with the row in `packages/core`.
4. Raise `syncSchemaVersion` and describe the table in `SYNC.md`. The end-to-end tests that speak the protocol themselves have the version written out: see "Sandboxes in `e2e`" below.
5. Add the table to the three places in the tests that list the tables by hand: the local copies of `SyncClient` in `apps/worker/test/sync-client.ts` and of `memoryWorkspace` in `packages/core/test/memory-transaction.ts`, and `shown()` in `apps/worker/test/app-client.ts`, which turns the view of the app's client into the form of the first to compare the two.

Nothing else in the server: the change log and the patches work on any table that `synced` lists. And nothing in the client: its store, its views and IndexedDB go by the names in `rowSchemas`, and a client that has rows of the schema before drops them and asks for all of them when it sees the new `syncSchemaVersion`. A screen reads the new table with `useSynced`.

A column that clients must not see goes into `schema.ts` and not into `synced.ts` and the row schema. It has to be nullable or have a default, because a mutator that creates a row writes only the synced columns. Code in the object reads and writes it with Drizzle, outside the mutators. A table that clients must not see is simply not listed. `sync.test.ts` has the tests that prove both: one for a column that is added to a table, and one for the credentials of a channel, the first real secret. A new secret column gets a case like the second.

**Add a mutator.** Add it to `mutators` in `packages/core/src/sync/mutators.ts`: a name, a strict Zod schema for its arguments and a function over the `Transaction`. It is synchronous, uses nothing but its arguments and the transaction, and takes the time from `tx.now`, because a client runs it too. It refuses by throwing `MutationRejected` with a code from `rejectionCodeSchema`. The state guards belong here, not in the callers. Unit-test it in `mutators.test.ts`, raise `syncSchemaVersion`, and add it to the table in `SYNC.md`. Then three things for the client:

- Say what the person is told when it is refused, in `apps/web/src/lib/mutations.ts`. The compiler asks for it. If its arguments carry text that somebody wrote, add it to `lostTexts` of the same file, with a case in `mutations.test.ts`: the notice of a refusal then offers to keep the text as a new draft.
- If the app makes many of them in a row of which only the last counts, as typing does with `part.setText`, add a rule to `supersedes` in `packages/core/src/sync/client/copy.ts`, and a test next to the one for `part.setText`. The outbox then keeps the last one while they wait to be sent, and so does a tab of those that it could not store. The rule has to be exactly true: running both mutations must do to the rows what running the later one alone does. It is only asked about two mutations that this version of the app has made: the outbox keeps the `syncSchemaVersion` with every mutation, and one of another version is never replaced.
- If it writes `tx.now` to a column that no mutator has written it to before, look at that column in `latestTime` in `packages/core/src/sync/client/view.ts` too. A change that is not confirmed is shown as later than every time that the server has put into the rows, so that a list sorted by time does not change its order when the confirmation arrives: `SYNC.md` section 4 has the rule. So far the only such column is `updatedAt` of a post.

A mutator that only the server may run gets `{ serverOnly: true }`: a client that sends it is rejected with `not_allowed`. That is for rows that stand for something only the server has, as a channel stands for credentials, and for what only the server knows, as how far a delivery has come. A mutator that reports on a delivery names the attempt it reports on and goes through `currentTarget`, which refuses a report that comes after the delivery has ended or begun anew. The Worker runs such a mutator with `mutateWorkspace`. If the row has columns that are not synced and have to change with it, add a method to `WorkspaceStore` that runs the mutator and writes them in one transaction, as `connectChannel` does. `disconnectChannel` does the same to hand out what a row held when it went.

**Change a workspace from Worker code**, without a client. The public API does so with a call of its own, `callWorkspaceApi`, which makes one change of several mutations: "Add a route to the public API" below. For one mutation: look the workspace up in D1, which is where it is decided whose it is, and call `mutateWorkspace(env.WORKSPACE, workspace, name, args)` from `src/workspace/workspaces.ts`. It runs the mutator in the workspace's object, and the clients that are connected receive the change. It answers `{ ok: true }` or the reason the mutator refused, and throws if the database of the workspace failed.

A call to `mutateWorkspace` cannot be repeated safely as it is. If it fails on the way, after the object has committed the change, the caller cannot tell, and a second call would run the mutator again. A caller that tries again passes a key as the last argument: `mutateWorkspace(env.WORKSPACE, workspace, name, args, key)`. The object carries a call with a key out once and keeps its outcome under the key, in the transaction of the change. A call that comes with the same key again changes nothing and is answered as the first was, refusal included, for 30 days. A call that threw has not happened and is carried out when it is repeated. The key is the caller's to make: the same for every repeat of one call, and for nothing else in the workspace. The steps of the publishing workflow use the ID of their run, what the call is for and a digest of what it says: a run that somebody restarts takes its steps again from the first, with other things to say under the same names. The public API has the `Idempotency-Key` of a request for it, together with the ID of the API key that sent it, and keeps a digest of the request with the status of the answer: the same key with another request is refused. It does not answer a repeat as the first call was answered: it keeps no body, and reads the post anew. A method of `WorkspaceStore` that does more than run a mutator gets the same guarantee by going through `once`, as `recordProgress` does, and `connectChannel`, whose call the connect callback repeats once when it throws. What such a method hands back besides is kept under the key with its outcome, so a secret among it is sealed: `connectChannel` hands back the access that a connection replaced, to a caller that asks for it with `handBack`.

**Replace the key that pigy signs with as a client of Bluesky.** `BLUESKY_CLIENT_KEYS` is a comma-separated list of `<version>:<key>`, each key the output of `openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:P-256 | openssl pkcs8 -topk8 -nocrypt -outform DER | openssl base64 -A`. The key with the highest version signs the connections that begin, and its `kid` in the client metadata is `pigy-<version>`. A connection to Bluesky stays bound to the key that it began with, and the credentials of its channel name it. So add a key with a higher version and keep the old one for as long as a channel that was connected with it is to go on: a channel whose key is gone asks to be connected again the next time its access is renewed, which is within minutes of its next post. A key that has leaked is removed at once, which is what ends the sessions that began with it.

**Replace the key that seals credentials.** `CREDENTIAL_KEYS` is a comma-separated list of `<version>:<key>`, each key the output of `openssl rand -base64 32`. Add a key with a higher version in front and keep the old one: the new one seals from then on, and the old one goes on opening what it sealed. Remove the old one only when nothing is left that it sealed, which a sealed value says at its start: `1.…` was sealed with version 1. The sealed values are `credentials` in the `channel` table of every workspace, and `registration` in `mastodon_app` and `pending` in `oauth_state` of D1. A fourth is there for minutes only: `outcome` in `keyed_call` of a workspace holds the credentials that a connection replaced, under `replaced`, until the first change of the workspace that comes five minutes or more after the connection, or until the channel of the account is disconnected. Nothing opens it after the request that connected the account. A key that is removed too early costs a new connection of every channel it sealed: the next post to such a channel fails, and marks the channel as `needs_reconnect`. Nothing seals a stored value again by itself yet: `PLAN.md` section 16 says where that belongs.

**Add a binding or variable.** Edit `apps/worker/wrangler.jsonc`, then run `pnpm typecheck`. It runs `wrangler types`, which regenerates the git-ignored `worker-configuration.d.ts` that declares `Env` and the runtime types. `pnpm install` generates it too. **Add a simulator** of a service that is not a social network. Add a directory to `packages/simulators/src` and an entry to `exports` in its `package.json`. A simulator answers on the real addresses of the service, as a function with the signature of `fetch` that fails for every other host. **Add a network.** `PLAN.md` section 6 says how each network maps onto the contract. Check that against the network's documentation first, and change the contract, with the plan, if it does not hold. Then, in this order, with the Worker and the screen last:

1. The limits. In `packages/core/src/network/limits.ts`, add a schema for what an account of the network may post to `limitsSchema`, and the network's way of counting to `countCharacters`. `validateContent` is what the browser and the Worker check content with, so a rule of the network that it does not have yet goes there.
2. The simulator, in `packages/simulators/src/<network>`, with an entry in `exports`. `src/mastodon` is the example:
   - It is `create<Network>Simulator(world)` and returns a `fetch` that answers on the network's real hosts and throws a `TypeError` for every other host, and `owns(host)`, which says whether a host is one of them. The world of a sandbox has the simulators of all networks, and goes by `owns` to find the one that a request is for.
   - It keeps everything in the world and nothing in itself: accounts, tokens and posts in the world's own tables, with more fields if it needs them, the rest in `world.table("<network>", ...)`. It makes its secrets with `simulatedSecret` or `world.issueToken`, and looks tokens up with `world.findToken`, which finds nothing that the world did not issue.
   - It is written from the network's documentation and enforces the network's rules itself: authentication, scopes, validation of every parameter, the counting of characters, what makes a repeated request safe, the bodies and statuses of errors, the rate limits. It keeps and hands out what the network would, which is not always what it was sent: Mastodon rewrites the mentions in a status. It imports nothing from `@pigy/providers` or `packages/core/src/network`. Refuse what is not simulated, do not ignore it. Mark what you had to assume with `GUESS` in a comment.
   - It takes its faults from `world.faults.take` with the kinds its network can suffer from, and declares them, with the kinds of request they can strike, as Mastodon's `mastodonFaultKinds` and `mastodonOperations`. A kind that the world does not have yet is added to `faultKinds` in `world/faults.ts` in the same change, with a test that shows the simulator applying it, as Threads added `slow-processing` for a container that takes long to be ready, and with its words in `apps/web/src/lib/simulator.ts`. The same goes for what a token or a post of the world lacks, such as a time at which a token ends.
   - Its consent page is `consentPage` of `world/pages.ts`, served for `GET` on the network's authorization address and answered with a `POST` to the same address, which carries `account` or `action=deny`. That is what lets `answerConsent` work for every network. It sends a browser only to a redirect address that was registered for the client, compared in full, never by its path or its host alone: the page is served at pigy's own address in a sandbox, where anybody can write its query. `simRoutes` passes on no redirect that leads to another origin all the same.
   - It keeps with a post what the network shows in it as more than text, `entities` of a `SimPost`, and the card of its link, `card`: found by itself where the network finds them, by its own rules, or as the post marked them, checked. That is what the feeds of a sandbox show, and what the conformance suite compares with `detectEntities`. A network that makes its cards itself reads the simulated web for them, `webPageAt` of `@pigy/simulators/web`.
   - It has tests of its own for the rules it enforces.
3. The adapter, in `packages/providers/src/<network>`, with an entry in `exports`: a function that takes `fetch`, the clock and what is the network's own, and returns a `Provider`. It sends requests with `send` of `src/http.ts`, checks every answer and everything that comes back from storage with a Zod schema, and reports every failure as a `ProviderError`. It catches nothing else. What `fetch` throws that is no failure of a network, and what a store that the adapter was made with throws, comes out of a method as it is, for the caller to log as a failure of pigy's: `send` sees to that for `fetch`, so do not wrap it. The comments in `src/provider.ts` are the contract. What an adapter gets wrong most easily:
   - `publishStep` makes at most one request that changes something, and a step can be run again at any time, a moment or days later, with the same request. It must not publish a part twice then, and it must not count on what the network remembers for a while. So before a request that publishes, the progress has to hold what a later run needs to find out whether the request was carried out, and a step that does not find it there returns it and sends nothing. `PLAN.md` section 8 has what that is for each network. Where the network offers nothing, a request to publish that ends without a clear answer fails with `uncertain`, never with `retry`, and the adapter says so with `repeatsSafely: false`: the workflow then never runs a step of it twice. LinkedIn's adapter is the example.
   - A step that looks for what an earlier run has published compares with what the network keeps, which is not always what was sent. It takes a post for its own only if the post is the same in everything that the step sends: the text, the place, who sees it, and what it has besides its text. It looks at nothing from before the delivery, whatever the network lists. And it counts on the caller to run the deliveries to one account one after the other, which the contract of `publishStep` requires: two that begin together with the same first part cannot be told apart.
   - The progress, the adapter's notes in `state` included, is stored as it is. No secret goes into it.
   - What the network wants marked in a text, the adapter marks with `detectEntities` of `@pigy/core`, which gets the network's way of writing a mention. A part may come with the card of its first link, `content.parts[n].card`, where `cardMaker` of `@pigy/core` says that pigy makes the card of the network: the adapter sends it, and never reads a page itself. A run can be handed another card than the run before it, or none, and what pigy takes for a link or a tag changes with a deploy, which can come between two runs of a step. So a step that looks for what an earlier run published never works out anew what that run sent besides the text: an adapter that sends marks or a card, as Bluesky's, makes them in a step that publishes nothing, with what it has to look up for them, as the account of a mention, and records them in its notes. The step that publishes sends exactly what was noted and compares with exactly that. Notes from before a field was there say what a step of that time sent: nothing.
   - `tellsDeliveriesApart` is `true` only if a step can never take the post of another delivery to the account for its own, however alike the two read. When in doubt it is `false`, which costs a second post in a rare case and never a post that two deliveries share.
   - A `ProviderError` of `completeConnect` is a `fail`, whatever went wrong at the network. The code of a callback is good once, so there is nothing to try again. Only what is no failure of a network comes out as it is, as from every method. What a callback says about a failure is quoted like the answer of a network, with `quotable`: without the secrets that `pending` holds, its `state` among them, and without the code of the callback. Anybody can send a browser to the callback address, and the message is logged.
   - `accessPerConnection` is `true` only if `disconnect` ends the connection that the credentials are from and no other of the same account. The connect callback goes by it: an access that it could not store is given back where that is so, and so is the access that a channel held before its account was connected again. Both are left alone where the network hands every connection the same access, as Mastodon does, because a channel may be using it. An adapter that says `true` and can fail in `completeConnect` after the network has handed over an access gives that access back itself before it fails, as Bluesky's does: its caller gets no credentials to do it with. The conformance suite holds an adapter that says `true` to it.
   - An adapter that has `refresh` fails with `refresh` when the network refuses credentials that a refresh would cure, whatever the time it has named in `refreshAt`. It fails with `reconnect` only when a refresh would not help.

**Run the conformance suite against a real network.** This posts to a real account. Use an account that is there for the purpose.

For Mastodon, sign in to the test account on its instance, open Preferences, Development, New application, and create one with the scopes `profile` (`read:accounts` before Mastodon 4.3), `read:statuses`, `write:statuses` and `write:media`.
```sh
PIGY_LIVE_MASTODON_INSTANCE=mastodon.example \
PIGY_LIVE_MASTODON_ACCESS_TOKEN=... \
PIGY_LIVE_MASTODON_CLIENT_ID=... \
PIGY_LIVE_MASTODON_CLIENT_SECRET=... \
pnpm --filter @pigy/providers conformance:live mastodon
```

- It runs `test/conformance/spec.ts` against the server, without the tests that take a simulation: consenting, arming a fault, moving the clock.
- It posts with the visibility `direct`, which only the account itself sees, and deletes every post after the test that made it. If a run is cut short, delete what begins with "pigy conformance" by hand.
- It registers one application named "pigy conformance run" with the instance, which Mastodon's API cannot remove.
- A run deletes about a dozen statuses, and Mastodon allows 30 deletions in 30 minutes. A third run within half an hour hits that limit, and then leaves posts behind. The run tries to delete every one of them and fails with the list of those it could not. Wait between runs.
- The script is the only way in. It refuses when `CI` is set and when a variable is missing. `test/live/setup.ts` refuses a run that the script did not start, and `pnpm test` does not find the files of the live run. Keep it that way: nothing else may lift the guard on `fetch`.
- Never put the credentials into a file of the repository.

The Chromium of the tests decides by itself whether it keeps what a site stores, by how much the site was used. `browserThat` in `device-storage.spec.ts` puts answers of the test's choosing in the place of `navigator.storage.persist()` and `persisted()`, and counts how often the app asks.
- Windows that a test stands in for in `e2e`. `silentWindow(page)` of `e2e/app.ts` is a window that holds the lock `pigy/unsaved` and answers nobody, as one that the browser has put aside: a page of the test on a file of the app, which runs no code of the app. `holdDeletions(page)` keeps the deletions of databases that a page asks for from the browser until `release()`, which makes the moment last in which a window deletes the local copies. A window that the browser has put aside hears of what the others stored when it wakes, all at once: a test dispatches those `storage` events itself, as the test of the window that slept in `sync-drafts.spec.ts` does. The `otherEmail` fixture is the address of a second person who is invited for the test alone, for somebody else who signs in on the device of `ownEmail`: not the admin, whose sessions a test that goes wrong there would end for every other test.
- Notifications in `e2e`. The Chromium of the tests has no push service and refuses notifications to every site, so no test shows one: `notifications.spec.ts` says at its top what is shown and what is not. `withPushService(context)` of `e2e/app.ts` gives a browser a push service: a page that subscribes is handed a device that the simulated push service of the e2e build has made up, under `/api/e2e/push`, and the person's answer to the browser's question is yes. `receivedBy(page)` is what that device has received from the built Worker, decrypted, and `pushEndpointOf(page)` its address. `notificationsRow` is the row of Settings, `openInbox`, `inboxLink` and `inboxItem` are the inbox, which a desktop has in its sidebar and a phone behind the bell in its header. A test that makes a delivery fail arms a fault that ends it at once, such as "Access taken back", which tells of two things: the post and the account. What the service worker does with a message is tested without a browser, in `apps/web/src/sw/push.test.ts`, with windows that a test makes up: `browser(...)` there, where `hears: false` is a window that does not answer.
- A server that never answers in `e2e`: a route that neither answers nor passes on, as `serverSilent` in `offline.spec.ts`, under a clock that the test moves by the ten seconds which the app gives the server.
- The service worker in `e2e`. Every test starts in a browser that has none, and the app installs one with its first page load, which then answers for the pages of the test: `serviceWorkerAnswersFor(page)` in `e2e/app.ts` waits for that, and a test that goes offline has to. From then on the files of the app and the app shell come from the device, so a `page.route` for one of them, or for a navigation to a screen, is no longer asked. A request to the API still passes through routes: the service worker does not answer it. The guard on other hosts covers the service worker, whose requests are requests of the browser context: `network-guard.spec.ts` shows it. The browsers that `invite` and `signInBeforeFirstLoad` open to sign somebody in have service workers switched off.
- A new version of the app in `e2e`. The server has one build, and Playwright cannot answer when a browser looks for a newer service worker, only when it fetches its first. So `olderVersionFirst(context)` hands the browser an older version first, made up from the build, and the build is the newer version that the browser finds when it looks: after a page load, or when the app asks. `update.spec.ts` shows how a test stays in charge of that moment. `holdNewer()` of what `olderVersionFirst` returns keeps the newer version from being installed until the test says, for what the app does while the device has only the older one. A test that says that a window has not loaded itself again for the newer version waits until the window has heard that the newer version took over, `takenOver` in `update.spec.ts`: a window that did not wait has begun to leave by then. Three things to know: the page load that installs the older version has to be the first of the browser, so the test signs in with `signInBeforeFirstLoad`. Never fail the registration of a service worker with a route: the Chromium of the tests then installs a new one with every page load, which looks like a bug of the app and is not. And the caches of the older version have a name of their own, which the newer version does not delete when it takes over: a test cannot show a window that misses a file of its build.
- The Worker under e2e makes no outbound requests. The e2e build has no Google credentials, so sign-in is answered inside the Worker, and a sandbox is answered by its simulated world. What is left is a live workspace, which talks to the real networks: in the e2e build, `outboundFetch` in `apps/worker/src/outbound.ts` gives the app a `fetch` that answers every request itself, with a 502. `connect.spec.ts` proves it, with a host under `.invalid`. So an end-to-end test connects accounts in a sandbox. Every sandbox has the same simulated accounts and the tests share the admin, so such a test is a person of its own and uses their sandbox: `ownPage`, as in `channels.spec.ts`. An answer of a route that this build cannot give, such as a network that did not take an access back, is given by the test in the route's place, with `page.route`.

## Deployment

`SETUP.md` is the guide for whoever runs a pigy: every step that is done by hand, in order, with a check after each. Nothing has been deployed yet, so what it says of Cloudflare is from the documentation, and `PLAN.md` section 19, "Launch (phase 11a)", lists what the first deploy has to confirm. This section is the reference that the guide points to: what the code relies on.

- CI deploys what is pushed to `main`, in the job `deploy` of `.github/workflows/ci.yml`, once every other job has passed, and when the workflow is started by hand on `main`. It is off until the repository variable `DEPLOY` is `true`, and its two secrets, `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`, are those of the environment `production`. It builds with `pnpm build`, applies the migrations of D1 and deploys. A push whose commit message has `[no deploy]` is not deployed. `PLAN.md` section 15 has what was decided. The job sets no secret of the Worker.
- A pull request that changes the names of the steps of the publishing workflow, or what they return, says so, and is merged with `[no deploy]` in the message of its merge commit unless it keeps the old names working: see the entry on a deploy and a delivery below.
- `wrangler.jsonc` turns Workers Logs on for what the Worker writes with `log`, and keeps the traces and the invocation logs off: `observability`. `PLAN.md` section 16, "The log", has why. Do not set `observability.enabled`, which turns the traces on with the logs.

- `wrangler.jsonc` binds two Durable Object classes, `WorkspaceDO` as `WORKSPACE` and `SimWorldDO` as `SIM_WORLD`, and declares them in `migrations` with `new_sqlite_classes`, in the entries `v1` and `v2`. The first `wrangler deploy` creates both classes with SQLite storage: nothing to set up beforehand. The entries must be right before that deploy, because the storage of a class cannot be changed afterwards, and an entry that has been deployed is never edited. Adding, renaming or deleting a class takes a new entry with a new tag.
- `wrangler.jsonc` binds the workflow `pigy-publish`, of the class `PublishWorkflow`, as `PUBLISH`. The first `wrangler deploy` creates it: nothing to set up beforehand. Its name is where the platform keeps its runs, so it is not renamed: a workflow under another name is another workflow, and the runs of the old one are orphans.
- Workflows are part of the Workers Paid plan as pigy needs them: on the free plan a step may use 10 milliseconds of CPU time, which is less than opening credentials and reading an answer take.
- A run of the workflow is kept by the platform for some days after it has ended, 7 on the paid plan unless the account says otherwise, with what it was started with and what its steps returned: the IDs of the workspace, the owner and the target, the text of the post, and what the adapter noted, such as the ID of the account at its network. No credentials. Deleting a post in pigy does not delete the runs that published it.
- A deploy does not interrupt a delivery. A run that is under way goes on with the new code at its next step, and takes the results of the steps before from the platform. So the names of the steps and what they return are a contract with the runs of the last version: a deploy that changes them while deliveries are under way leaves those runs to fail, and the object of their workspace then ends them as `uncertain`, for a person to look and try again. Deploy such a change when nothing is being sent, or keep the old names working for one deploy.
- The object of a workspace looks after its deliveries with its alarm, which needs nothing set up. A delivery whose run was terminated or deleted by hand, in the dashboard or with `wrangler workflows`, ends as `uncertain` within a minute. A run that is restarted there begins again from what the workspace has recorded, and publishes nothing twice.
- The databases of the workspaces need no step in a deploy. Their migrations are part of the Worker: the build puts each SQL file next to `index.js` as a module of its own, which `wrangler deploy` uploads with it.
- A deploy can close the sync sockets, and clients connect again by themselves. It can also leave a socket open under the new code. If the deploy raised `syncProtocolVersion` or `syncSchemaVersion`, the object closes such a socket the next time it is used, and clients that still run the old app are turned away until they have loaded the new one. A window of the old app then says "Reload to update" in its sync indicator, stops connecting and leaves the socket to a window that runs the new one. So does a window of the old app when another window has loaded the new one and brought the local copy to its schema. What is written in it meanwhile stays in the local copy and is sent after the reload.
- `wrangler.jsonc` binds a rate limiter, `API_RATE_LIMITER`, which counts the requests of each key of the public API: 120 in 60 seconds. It needs nothing set up: the first `wrangler deploy` creates it. Its `namespace_id`, 1001, is a number of this account's own choosing that no other limiter of the account may share, and a limiter with another number counts anew. The numbers of the limit are also in `apiRateLimit` of `packages/core/src/api/openapi.ts`, which the documentation and `Retry-After` are made from: change both. The platform counts per location and catches up with a delay, so a key can get somewhat past the limit: `PLAN.md` section 19.
- The public API needs no secret and no setup besides. Its keys are rows of D1, made in the app. `/api/v1/docs` and `/api/v1/openapi.json` are served to anybody, and say nothing of anybody.
- The D1 database has no `database_id` in `wrangler.jsonc`. The first `wrangler deploy` creates a database named `pigy` and binds it, and later deploys keep the binding. Wrangler 4.162 does this by default. Migrations are applied to it with `wrangler d1 migrations apply DB --remote`.
- The Worker needs ten secrets: `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `ADMIN_EMAILS`, `CREDENTIAL_KEYS`, `BLUESKY_CLIENT_KEYS`, `LINKEDIN_CLIENT_ID`, `LINKEDIN_CLIENT_SECRET`, `THREADS_APP_ID`, `THREADS_APP_SECRET` and `VAPID_PRIVATE_KEY`. Without the first two nobody can sign in. The Google client needs the redirect address `https://<host>/api/auth/google/callback`.
- `CREDENTIAL_KEYS` is `1:<key>`, with the output of `openssl rand -base64 32` as the key: `wrangler secret put CREDENTIAL_KEYS`. Without it no account can be connected, in a sandbox no more than for real, and nothing can be published: every delivery fails with a target that says so. Keep a copy of it somewhere safe: the credentials of every channel are worthless without it. "Replace the key that seals credentials" above says how it is changed.
- `BLUESKY_CLIENT_KEYS` is `1:<key>`, with the output of the `openssl` command of "Replace the key that pigy signs with as a client of Bluesky" above as the key: `wrangler secret put BLUESKY_CLIENT_KEYS`. Without it no Bluesky account can be connected, in a sandbox either, and a Bluesky channel cannot renew its access.
- `LINKEDIN_CLIENT_ID` and `LINKEDIN_CLIENT_SECRET` are the client ID and the client secret of an application that you make at https://www.linkedin.com/developers/apps, which LinkedIn wants linked to a LinkedIn Page: `wrangler secret put` each. The application needs the products "Share on LinkedIn" and "Sign In with LinkedIn using OpenID Connect", and the redirect address `https://<host>/connect/linkedin/callback`, character by character. Without the two secrets no LinkedIn account can be connected in a live workspace, and one that is connected goes on posting until its access ends, after 60 days, but cannot give its access back when it is disconnected. A sandbox needs neither. LinkedIn retires a version of its API about a year after it came out: `linkedInApiVersion` in `packages/providers/src/linkedin/index.ts` has to be raised before then, in the code.
- `THREADS_APP_ID` and `THREADS_APP_SECRET` are the Threads app ID and the Threads app secret of an app that you make at https://developers.facebook.com/apps with the use case "Access the Threads API": the two values of that use case, not the ID and the secret of the Meta app around it. `wrangler secret put` each. The use case needs the permissions `threads_basic`, `threads_content_publish`, `threads_manage_replies`, `threads_read_replies` and `threads_delete`, and the redirect callback address `https://<host>/connect/threads/callback`, character by character. Until Meta has reviewed the app for those permissions, only the accounts that you add to it as Threads testers can be connected, and each of them accepts the invitation in the settings of their Threads account first: add every person whom you invite to pigy and who posts to Threads. The settings of the use case also have fields for an uninstall callback URL and a delete callback URL, which Meta may require (a guess, `PLAN.md` section 19). Enter `https://<host>/connect/threads/uninstall` and `https://<host>/connect/threads/delete` for now. Nothing answers at them yet: pigy hears that a person has removed it when the next post or the next renewal is refused. Without the two secrets no Threads account can be connected in a live workspace. One that is connected goes on posting, and its access is renewed, without them. A sandbox needs neither.
- The access of a Threads channel lasts 60 days and is renewed by the alarm of its workspace, a week after it was issued and every week from then on, which needs nothing set up. Threads renews no access that has ended, so a pigy that could not reach Threads for all of those weeks, or that was without `CREDENTIAL_KEYS` for them, leaves channels that have to be connected again: they say so, and from two weeks before the end the row of such a channel names the day. A Bluesky channel is renewed the same way, and waits for `BLUESKY_CLIENT_KEYS` where that is missing. The token of a Threads account travels in the address of the requests that read, as Meta documents it: do not turn on the traces or the logs of outbound requests that Cloudflare offers for the Worker, `PLAN.md` section 16. `wrangler.jsonc` says that the traces are off. The timer does not know who is still invited: the channels of a person who was removed keep their access, `PLAN.md` section 6. Nothing gives the access of a Threads channel back when it is disconnected, because Meta has no way for that: the person is told where to remove pigy in the settings of their account.
- `VAPID_PRIVATE_KEY` is the key that pigy signs push messages with: the output of `openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:P-256 | openssl pkcs8 -topk8 -nocrypt -outform DER | openssl base64 -A`, by itself: `wrangler secret put VAPID_PRIVATE_KEY`. Without it Settings say that notifications are not set up, and nothing is sent. The inbox works all the same. Keep a copy: a browser subscribes with the public half of this key, so a new key turns the notifications of every device off until each has turned them on again. Nothing else is to set up: every browser names its own push service, and pigy tells that service its own address as the contact of the sender.
- A deploy does not lose push messages. The ones that wait are in the database of their workspace, and its alarm sends them when it next runs.
- Connecting accounts needs nothing else. The networks send the browser back to `https://<host>/connect/<network>/callback`, a path that `assets.run_worker_first` sends to the Worker. Mastodon needs no registration by hand: pigy registers itself with each instance, with that address, the first time somebody connects an account there. Bluesky needs none either: it reads pigy's client metadata from `https://<host>/connect/bluesky/client-metadata.json`, which is pigy's client ID. LinkedIn and Threads are the two networks with a registration by hand, above. Moving pigy to another address makes it another client of Bluesky, `PLAN.md` section 20.
- The web app is deployed with its service worker, which needs no step of its own. After a deploy, a device goes on running the version that it has until it has fetched the new one, which waits for the app to be started again: `PLAN.md` section 13. A deploy that raises `syncProtocolVersion` or `syncSchemaVersion` does not wait for that: the windows that are open say "Reload to update", and the reload loads the new version.
- `apps/web/public/_headers` is part of the build. It lets browsers keep what is under `/assets/` for a year, and has the content security policy of the app, with hashes that the build has written. A path under `/assets/` that has no file is a 404 from the Worker, which nothing keeps. In a zone of the owner's, nothing may change `index.html` on its way to the browser: the policy allows its inline script by the hash of its exact text.
- Always deploy right after `pnpm build`, never after `pnpm preview:e2e` or `pnpm e2e`. Each build points `wrangler deploy` at itself, through `apps/web/.wrangler/deploy/config.json`, and the e2e build contains the simulated sign-in.

## Tool versions

- The Workers test integration is `@cloudflare/vitest-plugin`, the renamed `@cloudflare/vitest-pool-workers`. It supports Vitest 4.1 and 5. This repository uses Vitest 5.
- Cloudflare Workflows are tested with what `cloudflare:test` has for them, `introspectWorkflow` and `introspectWorkflowInstance`, from `@cloudflare/vitest-plugin` 1.0 on. The class of the workflow runs in the isolate of the test, like the Durable Objects, and `reset()` deletes its runs. Three things differ from production: a run that waits says `running` where production says `waiting`, the status of a run lists the results of its steps under `__LOCAL_DEV_STEP_OUTPUTS`, and an error that is thrown out of a step arrives in `run` as a plain `Error` whose message begins with the name of the class.
- `@playwright/test` is pinned to an exact version because each version needs its own browser build. After changing it, run `pnpm --filter @pigy/e2e exec playwright install chromium`.
- Drizzle is `drizzle-orm` 0.45 with `drizzle-kit` 0.31, the stable line. Version 1 is in beta and stores migrations differently. D1 uses `drizzle-orm/d1`, the workspaces `drizzle-orm/durable-sqlite`, which is synchronous. `drizzle.config.ts` is for the first, `drizzle.workspace.config.ts` for the second.
- Versions shared by several packages are in the `catalog` of `pnpm-workspace.yaml`.
- pnpm refuses install scripts and agent skills from dependencies unless `permissions` in `pnpm-workspace.yaml` allows them. If `pnpm install` reports a package awaiting approval, decide there. Do not add `allowBuilds`: `permissions` overrides it.
