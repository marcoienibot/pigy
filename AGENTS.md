# Working on pigy

`PLAN.md` is the design: architecture, naming, repository layout and what each phase delivers. Read it before starting a phase. `SYNC.md` is the protocol through which clients keep a copy of a workspace and change it.

## Setup

- Node.js 22 (`.nvmrc`).
- pnpm 12, pinned by `packageManager` in `package.json`. Install it without sudo with `npm install -g --prefix ~/.local pnpm` and make sure `~/.local/bin` is on `PATH`. `corepack pnpm` does not work: the corepack bundled with Node 22 cannot run pnpm 12.
- `pnpm install`

Nothing else: `pnpm dev` needs no configuration, no Google project and no Cloudflare account.

## Commands

Run from the repository root.

| Command | What it does |
| --- | --- |
| `pnpm dev` | Web app with hot reload and the Worker in the local Workers runtime, both on http://localhost:5173. Brings the local database up to date first |
| `pnpm build` | Production build of the web app and the Worker into `apps/web/dist`. Fails if the build contains the simulated sign-in or the development key |
| `pnpm preview` | Builds for production and serves that build in the local Workers runtime, on http://localhost:4173. Sign-in needs Google credentials, see below |
| `pnpm preview:e2e` | Builds the app that `pnpm e2e` tests and serves it on http://localhost:4173, to try a built app by hand. Port 4173 must be free |
| `pnpm lint` | Biome lint, format and import order check |
| `pnpm format` | Biome fixes for the above |
| `pnpm typecheck` | `tsc` in every package |
| `pnpm test` | All Vitest suites |
| `pnpm e2e` | Runs `pnpm preview:e2e`, then Playwright against it. Port 4173 must be free |

One package: `pnpm --filter @pigy/worker test`. One file: `pnpm --filter @pigy/worker test test/health.test.ts`. Watch mode: `pnpm --filter @pigy/core exec vitest`.

`pnpm --filter @pigy/providers conformance:live <network>` is not part of any of these. It posts to a real account, see "Run the conformance suite against a real network" below.

## Signing in locally

Sign-in is with Google. Without Google credentials, a simulated Google stands in for it: "Sign in with Google" leads to a page of the app itself, labelled as a simulation, where you say who you are. Any email address works, no password.

- `pnpm dev` after a fresh clone: sign in as `admin@example.com`, which the simulated page offers with one click. It is the admin. Invite other addresses under Settings → Access, then sign in as them the same way.
- To change the admins, or to sign in with the real Google, copy `apps/worker/.dev.vars.example` to `apps/worker/.dev.vars` and follow the comments in it.
- `pnpm preview:e2e` always simulates, with `admin@example.com` as the admin, and starts from an empty database every time. It ignores `.dev.vars`.
- `pnpm preview` serves the production build, which has no simulated sign-in. Without Google credentials in `.dev.vars` its sign-in page says that sign-in is not set up.
- The browser keeps who is signed in under `pigy-session` in `localStorage`, and a copy of each workspace in an IndexedDB database named `pigy/<user ID>/<workspace ID>`. Signing out deletes both. `pnpm preview:e2e` empties the server's database and not the browser's: after it, the browser holds a session that the server does not know, and the app goes to the sign-in page as soon as it has asked.

Which Google is used is decided per request, in `accessConfig` in `apps/worker/src/auth/config.ts`: the real one if `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` are set. Otherwise the simulated one, if the build has it and the request names a local host, as described below. Otherwise sign-in is refused.

The simulated sign-in signs anybody in as anybody, so it must never be deployed:

- `apps/worker/src/index.ts` builds it in only when the Vite mode is `development`, `test` or `e2e`. In a production build the bundler drops it.
- `pnpm build` runs `apps/web/scripts/check-build.mjs`, which fails if the production build contains it. `pnpm preview:e2e` runs the same script the other way round, to prove that the check still knows what to look for. If you rename something in the simulated sign-in, that run tells you to update the script. The script looks for the development key of the next section in the same way.
- It answers only a request whose URL has a local hostname: `localhost`, a name that ends in `.localhost`, `127.0.0.1` or `[::1]`. That is `isLocal` in `apps/worker/src/auth/config.ts`. The Worker reads the hostname from the URL of the request, which comes from its `Host` header: it says what the client asked for, not where the client is. So a dev or e2e build that is exposed to a network, for example with `vite --host` or through a tunnel, lets anyone who sends a local `Host` header sign in as anybody. Keep those builds on the local machine.

## Connecting accounts locally

Every user has a live and a sandbox workspace. An account that is connected in the live one is a real one. In the sandbox it is one of the simulated accounts of that workspace's own simulated world, and nothing leaves the Worker. `PLAN.md` section 6 has the routes.

- The credentials of a connected account are sealed before they are stored, with the keys in the secret `CREDENTIAL_KEYS`. Without it, `pnpm dev`, `pnpm preview:e2e` and the tests seal with a key from the repository, `apps/worker/src/development-keys.ts`, so nothing has to be set up. That key protects nothing. It is built in under the same condition as the simulated sign-in, is used only where the app is reached at a local host, and must never be deployed. A production build without `CREDENTIAL_KEYS` refuses to connect accounts.
- There is no screen for it yet. To connect a simulated account by hand, run `pnpm dev`, sign in, and enter this in the console of the browser:

  ```js
  const { workspaces } = await (await fetch("/api/workspaces")).json();
  const sandbox = workspaces.find(({ environment }) => environment === "sandbox");
  const response = await fetch(`/api/workspaces/${sandbox.id}/connect`, {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ network: "mastodon", identifier: "mastodon.example" }),
  });
  location.href = (await response.json()).url;
  ```

  The page that opens is the consent page of the simulated Mastodon, labelled as a simulation. Choose an account. The browser comes back to `/channels?connect=connected&…`. The channel is a row of the synced table `channel`, and `DELETE /api/workspaces/<workspace ID>/channels/<channel ID>` removes it.
- To connect a real Mastodon account, do the same with the `live` workspace and the domain of your instance. `pnpm dev` reaches the internet. `pnpm preview:e2e` does not: there every request of a live workspace to a network is answered with an error.

## Layout

| Path | Contents |
| --- | --- |
| `apps/web` | React 19, TanStack Router, Tailwind CSS v4, shadcn/ui. Its `vite.config.ts` builds and serves both the web app and the Worker |
| `apps/worker` | Hono app, `wrangler.jsonc`, the D1 schema and its migrations, the Durable Object of a workspace with its own schema and migrations, tests that run in the Workers runtime |
| `packages/core` | Zod schemas and domain code shared by web and Worker. Consumed as TypeScript source, no build step. `src/sync` holds what client and server of the sync protocol share: the synced tables, the mutators and the messages. `src/sync/client` is the client of the protocol, as far as it needs no browser. `src/network` holds what an account may post on a network and how its text is counted |
| `packages/providers` | The contract between pigy and a network, and the adapters that implement it. So far Mastodon. Consumed as TypeScript source: `@pigy/providers` is the contract, `@pigy/providers/mastodon` an adapter |
| `packages/simulators` | Stand-ins for external services, written from their documentation. So far Google sign-in and Mastodon. Consumed as TypeScript source, one entry point per service: `@pigy/simulators/google`, `@pigy/simulators/mastodon`, and `@pigy/simulators/world` for what the simulated networks share |
| `e2e` | Playwright tests |

Imports:

- `apps/web` imports `@pigy/core`. `apps/worker` imports `@pigy/core`, `@pigy/providers` and `@pigy/simulators`. The apps never import each other.
- `packages/core` imports nothing from the apps or the other packages. It runs in the browser and in the Worker, so it uses only the web-standard APIs that both have, such as `URL`, `crypto` and `TextEncoder`, and no browser-only, Node or Workers APIs.
- `packages/providers` imports `@pigy/core` and nothing from the apps. It runs in the Worker, and in Node for its own tests, so the same limits apply. Its tests, and only its tests, import `@pigy/simulators`.
- `packages/simulators` imports `@pigy/core` and nothing from the apps. It runs in the Worker, and in Node for its own tests, so the same limits apply. It never imports `@pigy/providers`, and the simulator of a network uses nothing of `packages/core/src/network`: it checks what the adapter and pigy's own validation do, so it shares no code with them.
- For all three packages Biome rejects `window`, `document`, `localStorage`, `process` and `Buffer`, and Node modules in the source. The source is type-checked without Node types (`tsconfig.src.json`), the tests with them (`tsconfig.test.json`).
- `e2e` imports no application code.

In `packages/providers/src`: `provider.ts` is the contract, `errors.ts` the one error that every adapter fails with, `publish.ts` the loop that publishes a post step by step, `http.ts` how adapters send a request. Each network has a directory. `test/conformance` holds the specification that every adapter passes.

In `packages/simulators/src`: `world/` is what the simulated networks share: the storage, the world with its accounts, tokens and posts, the clock, the faults and the consent page. It also has what every simulation is made with, such as the frame of a page in `pages.ts`. Each service has a directory. `google/` is not part of a production build and keeps nothing in a world. It may import from `world/`. Nothing in `world/` or in the directory of a network imports from `google/`: that would carry the simulated sign-in into a production build.

In `apps/web/src`:

- `routes/` has the screens. `routes/_app.tsx` is where the app learns who is signed in and opens the workspace.
- `sync/` is what the sync client takes from a browser. `indexed-db.ts` stores the local copy. `workspace-sync.ts` starts the sync of a workspace in a tab: the store, the `BroadcastChannel` between the tabs, the Web Lock that decides which tab holds the socket, and the WebSocket. `react.tsx` has the hooks that screens use.
- `lib/session.ts` keeps who is signed in on the device, asks the server whether that still holds, and deletes the local copies when it does not. `lib/api.ts` has the calls to the API.
- `lib/drafts.ts` is an example of what a screen is built on: a function from the synced tables to what the screen shows, and hooks for what it does.
- `components/` has the app shell and what every screen shares: the command palette, the sync indicator, the notices of refused changes. `components/ui` is shadcn/ui.

In `packages/core/src/sync/client`, in the order in which a change passes through them:

- `copy.ts` is the local copy and every way it changes, as pure functions from what is stored to what to write: applying a patch, giving a mutation its ID, choosing what to send, starting over. The rules of `SYNC.md` for a client are here.
- `view.ts` computes what to show: the rows of the server with the unconfirmed mutations run on top. It also chooses the time that each of them is run at, which is the device's only where that keeps the mutation later than what the server has confirmed.
- `store.ts` is `SyncStore`, the copy as one tab holds it in memory: what screens read, `mutate`, and keeping in step with the other tabs. It is also where a tab finds out that it is too old for the copy, and that a mutation could not be stored, which the tabs tell each other.
- `connection.ts` is `SyncConnection`, which the one tab that holds the socket runs: hello, patches, sending the outbox, close codes, connecting again. What it writes for a socket goes through `forSocket`, which writes nothing once the socket has been given up.
- `storage.ts` is what a store asks of where the copy is kept, and `memory.ts` keeps one in memory, for tests.

In `apps/worker/src`: `index.ts` is the entry point and only chooses what the app and the Durable Objects are built with. `app.ts` puts the routes together. `auth/` holds sign-in, sessions and the guards for routes, `admin/` the allowlist API, `db/schema.ts` the schema of D1.

What connects accounts:

- `channels/routes.ts` has the routes that connect and disconnect an account, and is the only code that sees credentials in the clear. `channels/pending.ts` keeps the connections that have begun, in the table `oauth_state` of D1.
- `network/providers.ts` makes the adapter of a network for a workspace: `providerOf`. `network/reach.ts` decides where the requests of that adapter go, by the environment of the workspace: `reachOf`. `network/mastodon-apps.ts` is where the Mastodon adapter keeps its registrations, the table `mastodon_app` of D1.
- `sim/` holds the simulated worlds of the sandboxes. `object.ts` is the Durable Object of a world, of the class `SimWorldDO`. `world.ts` is the Worker's side: `worldFetch`, the only way into an object, and the addresses of the pages of a world. `routes.ts` serves those pages under `/sim/network`.
- `vault.ts` seals and opens what is stored of secrets. `development-keys.ts` has the key that stands in for `CREDENTIAL_KEYS` in development, and is not part of a production build.
- `outbound.ts` chooses the `fetch` that the app reaches the outside with, by the mode of the build.

`workspace/` holds the data of the workspaces. Each workspace is a Durable Object of the class `WorkspaceDO` with a SQLite database of its own:

- `object.ts` is the object: its sockets and the messages of the sync protocol.
- `store.ts` is its database: it runs mutators, numbers the changes, keeps the rejections that a client has yet to hear of and works out what a client is missing. It also stores what a channel has besides its row: the sealed credentials.
- `schema.ts` has its tables, `migrations/` what `drizzle-kit` generates from them.
- `synced.ts` lists the columns that clients get to see, and is the only code that reads or writes them.
- `workspaces.ts` is the Worker's side: the `workspace` table of D1, and the only ways into an object: `connectWorkspace` for a client, and `mutateWorkspace`, `connectChannel`, `disconnectChannel` and `channelAccess` for the Worker's own code.
- `routes.ts` has `GET /api/workspaces` and the WebSocket endpoint `/sync/<workspace ID>`.

## Rules

- Tests never reach a real network host. External services are simulated.
- No tautological tests. When a test step or assertion is not obvious, add a comment saying why it is there.
- Code that talks to external services takes `fetch` and the clock as parameters, typed `Fetch` and `Clock` from `@pigy/core`. It never uses the globals. In the Worker both come from `createApp` in `src/app.ts`. The sync client takes its timers the same way, typed `Schedule`, so that its tests wait for nothing.
- A `Fetch` fails with a `TypeError` when no answer comes, as the Fetch standard has it, and with nothing else then. `send` of `@pigy/providers` takes a `TypeError`, and a request whose time is up, for a network that is out of reach, and asks to try again. Whatever else a `fetch` throws is passed on as it is and ends in the log as a failure of pigy's: a check in the simulated world of a sandbox that refuses, a bug in a simulator. The Workers runtime fails with a plain `Error` when a connection is lost, so `outboundFetch` in `apps/worker/src/outbound.ts` turns what the runtime's `fetch` throws into a `TypeError`. A simulator throws a `TypeError` for a host that is not its own and for an answer that a fault loses, and for nothing else.
- A network is reached through its adapter in `packages/providers` and in no other way. What an adapter hands out to be stored, credentials above all, is opaque: store it, hand it back, never read it.
- In the Worker, an adapter is made by `providerOf` in `src/network/providers.ts` and in no other way. It gives the adapter the `fetch` of its workspace: the simulated world of a sandbox, the app's own `fetch` for a live workspace. Nothing else may choose, and nothing in a request may influence it.
- Secrets that are not pigy's own are sealed with `src/vault.ts` before they are stored: the credentials of a channel, a registration with a network, what a connection in progress needs. They are opened only where an adapter is called with them. They never go into a log, an error, a sync message or an answer, and neither does an error that could hold one: log the message of a `ProviderError` or a `VaultError`, which hold none.
- Nothing that crosses into a Durable Object or out of it is a `Request`, a `Response` or a stream. Pass plain data, read whole. A body that crosses as a stream keeps the call open until somebody has read it, and code that refuses a request early does not read it.
- What a network or a person says is untrusted. A host that a person names is validated before a request goes to it. What a network puts into an error reaches a message only through `quotable` of `@pigy/providers`, which takes the secrets of the request out.
- Validate data at boundaries with Zod schemas from `packages/core`. Share types, do not duplicate them.
- The synced data of a workspace changes only through mutators from `packages/core`, run by the workspace's Durable Object. No other code writes to a synced table.
- A screen reads synced data from the local copy and changes it with a mutator. It does not fetch synced data, does not wait for the server and has no loading state for it. Only what is not synced, such as the allowlist, goes through `lib/api.ts`.
- `SYNC.md` is the contract with the clients. Change it in the same change as the code. Raise `syncProtocolVersion` when the messages or their meaning change and `syncSchemaVersion` when the synced tables or the mutators do: a client that speaks another version is turned away until it has updated itself.
- No secrets in the repository. Local secrets go in `apps/worker/.dev.vars`, which is git-ignored.
- `PLAN.md` is the design. If an implementation must deviate, update `PLAN.md` in the same change and say why.

## How to

**Add a screen.** Create `apps/web/src/routes/_app/<name>.tsx` with `createFileRoute` and wrap the content in `<Page title="…">`. `actions` puts buttons next to the title, and `fill` hands the screen the whole body to lay out, as the drafts screen does for its two panes. Everything under `_app` needs a session: `_app.tsx` learns who is signed in before anything renders and puts it into the route context, `Route.useRouteContext().me`, with the workspace that is open. On a device that has been signed in before, that is the word of the device, which the server is asked about in the background: see `lib/session.ts`. A screen for people who are not signed in goes next to `sign-in.tsx` and uses `<PublicPage>`. The dev server and the build regenerate `src/routeTree.gen.ts`: commit it, never edit it. Add the route to `navItems` in `src/components/app-shell.tsx` if it belongs in the navigation, and to `screens` in `src/components/command-palette.tsx`.

**Read synced data in a component.** `useSynced(select)` from `@/sync/react` hands `select` the synced tables, each a `Map` from ID to row, and returns what it returns. The tables are what to show: the rows of the server with the changes of this device that are not confirmed yet. The component renders again when a row changes. Write `select` as a function of its own in `src/lib`, like `selectDrafts` in `lib/drafts.ts`: it has to be the same function on every render, and it is where sorting and joining belong. A row that has not changed is the same object in every view, so a `select` that makes items for a list can hand out the item it made of that row before, as `draftOf` does there. A row component wrapped in `memo` then renders only when its item has changed, which is what keeps typing cheap in a long list. There is nothing to wait for and nothing to fail, so no loading or error state. In an event handler, `useSyncedNow()` returns a function that reads the tables without making the component render. `useSyncState()` says how sync is getting on, for the indicator in the shell: the connection, how many changes the server has not confirmed, and how many of them the device could not store. Whatever warns before work is discarded has to count the last ones too, in every tab: they are in no database. `store.unsavedInAllTabs()` asks the other tabs for theirs, as the sign-out in `components/user-menu.tsx` does.

**Change synced data from a component.** `const mutate = useMutate()`, then `mutate("part.setText", { id, text })`: the name of a mutator and its arguments, checked by the compiler. It returns at once and the change is on screen, in every tab. Make up the ID of a new row with `uuidv7(new Date())`. There is no result to wait for: if the server refuses the mutation, the change is taken back and `Rejections` in `components/rejections.tsx` tells the person. A field that is typed into can call `mutate` on every keystroke, as the editor of a draft does.

**Add a keyboard shortcut or a command.** `useShortcuts` in `src/lib/keyboard.ts` hands a screen the key presses that are not typing and not meant for a dialog or a menu. A shortcut that works on every screen, and every command of the palette, goes into `components/command-palette.tsx`. Show the keys where the thing is done: `Kbd` in a button, a tooltip or the palette.

**Add a shadcn/ui component.** Run `pnpm --filter @pigy/web exec shadcn add <name>`, then `pnpm format` from the root. This runs the `shadcn` version that `apps/web` depends on, the same one whose CSS its styles import. Components land in `apps/web/src/components/ui`. Theme tokens are in `apps/web/src/styles.css`. If the command asks whether to overwrite a component that exists, say no. The components are written for Next.js: delete a `"use client"` line, and replace `next-themes` with `useTheme` from `components/theme-provider.tsx` and remove the package, as `ui/sonner.tsx` shows.

**Add an API route.** Add it to a group of routes under `/api/` in `apps/worker/src`, or add a group and mount it in `app.ts`. Put the request and response schemas in `packages/core` and parse with them on both sides: `parseJsonBody` in `src/errors.ts` does it for a request body. To refuse a request, throw Hono's `HTTPException` with the status and a message for the client. It becomes an error response in the shape of `errorResponseSchema`, with the error name that `PLAN.md` section 12 gives the status. Any other exception becomes a JSON 500 that says nothing about it. Guard a route with `requireUser`, and `requireAdmin` after it, from `src/auth/guards.ts`: the first also refuses requests that change something and do not come from pigy's own pages. In the web app, call the route through `request` in `apps/web/src/lib/api.ts`. Only `/api/*`, `/sim/*` and `/sync/*` reach the Worker. Every other path is a static asset or the app shell, so a new prefix such as `/connect` must be added to `assets.run_worker_first` in `wrangler.jsonc`.

**Change the database schema.** There are two databases. Never edit a migration of either that is on `main`.

- D1 holds sign-in and what is global. Edit `apps/worker/src/db/schema.ts`, run `pnpm --filter @pigy/worker db:generate --name <what_changed>` and commit the files it adds to `apps/worker/migrations`. The migrations are applied by `pnpm dev`, `pnpm preview` and `pnpm preview:e2e` when they start, and by `test/setup.ts` before every Worker test.
- Every workspace has a SQLite database in its Durable Object. Edit `apps/worker/src/workspace/schema.ts`, run `pnpm --filter @pigy/worker workspace:generate --name <what_changed>` and commit what it adds and changes in `apps/worker/src/workspace/migrations`. That includes `migrations.js`, which imports the SQL files and is how they get into the Worker. Nothing applies these migrations from outside: each object applies them to its own database when it starts, so after a deploy a workspace is migrated the next time it is used. A migration therefore has to work on a database of any age, and the code must not assume that all workspaces change at once.

**Add a synced table**, one that clients hold a copy of.

1. Describe its rows in `packages/core/src/sync/tables.ts`: a strict Zod schema with an `id`, added to `rowSchemas`. Add `putSchema("<table>")` to `changeSchema` in `protocol.ts`.
2. Add the table to `apps/worker/src/workspace/schema.ts` and generate the migration. No "on delete cascade" and no triggers: a row that the database changes by itself is a change that no client hears of.
3. List the table and its synced columns in `synced` in `apps/worker/src/workspace/synced.ts`. The compiler compares the list with the row in `packages/core`.
4. Raise `syncSchemaVersion` and describe the table in `SYNC.md`.
5. Add the table to the three places in the tests that list the tables by hand: the local copies of `SyncClient` in `apps/worker/test/sync-client.ts` and of `memoryWorkspace` in `packages/core/test/memory-transaction.ts`, and `shown()` in `apps/worker/test/app-client.ts`, which turns the view of the app's client into the form of the first to compare the two.

Nothing else in the server: the change log and the patches work on any table that `synced` lists. And nothing in the client: its store, its views and IndexedDB go by the names in `rowSchemas`, and a client that has rows of the schema before drops them and asks for all of them when it sees the new `syncSchemaVersion`. A screen reads the new table with `useSynced`.

A column that clients must not see goes into `schema.ts` and not into `synced.ts` and the row schema. It has to be nullable or have a default, because a mutator that creates a row writes only the synced columns. Code in the object reads and writes it with Drizzle, outside the mutators. A table that clients must not see is simply not listed. `sync.test.ts` has the tests that prove both: one for a column that is added to a table, and one for the credentials of a channel, the first real secret. A new secret column gets a case like the second.

**Add a mutator.** Add it to `mutators` in `packages/core/src/sync/mutators.ts`: a name, a strict Zod schema for its arguments and a function over the `Transaction`. It is synchronous, uses nothing but its arguments and the transaction, and takes the time from `tx.now`, because a client runs it too. It refuses by throwing `MutationRejected` with a code from `rejectionCodeSchema`. The state guards belong here, not in the callers. Unit-test it in `mutators.test.ts`, raise `syncSchemaVersion`, and add it to the table in `SYNC.md`. Then three things for the client:

- Say what the person is told when it is refused, in `apps/web/src/lib/mutations.ts`. The compiler asks for it.
- If the app makes many of them in a row of which only the last counts, as typing does with `part.setText`, add a rule to `supersedes` in `packages/core/src/sync/client/copy.ts`, and a test next to the one for `part.setText`. The outbox then keeps the last one while they wait to be sent, and so does a tab of those that it could not store. The rule has to be exactly true: running both mutations must do to the rows what running the later one alone does. It is only asked about two mutations that this version of the app has made: the outbox keeps the `syncSchemaVersion` with every mutation, and one of another version is never replaced.
- If it writes `tx.now` to a column that no mutator has written it to before, look at that column in `latestTime` in `packages/core/src/sync/client/view.ts` too. A change that is not confirmed is shown as later than every time that the server has put into the rows, so that a list sorted by time does not change its order when the confirmation arrives: `SYNC.md` section 4 has the rule. So far the only such column is `updatedAt` of a post.

A mutator that only the server may run gets `{ serverOnly: true }`: a client that sends it is rejected with `not_allowed`. That is for rows that stand for something only the server has, as a channel stands for credentials. The Worker runs such a mutator with `mutateWorkspace`. If the row has columns that are not synced and have to change with it, add a method to `WorkspaceStore` that runs the mutator and writes them in one transaction, as `connectChannel` does. `disconnectChannel` does the same to hand out what a row held when it went.

**Change a workspace from Worker code**, without a client, as the REST API will. Look the workspace up in D1, which is where it is decided whose it is, and call `mutateWorkspace(env.WORKSPACE, workspace, name, args)` from `src/workspace/workspaces.ts`. It runs the mutator in the workspace's object, and the clients that are connected receive the change. It answers `{ ok: true }` or the reason the mutator refused, and throws if the database of the workspace failed.

A call to `mutateWorkspace` cannot be repeated safely. If it fails on the way, after the object has committed the change, the caller cannot tell, and a second call would run a mutator again that is not idempotent. Callers that retry, which are the publishing pipeline in phase 3 and the REST API in phase 6, need one of two things: mutators that are idempotent by design, or a `mutateWorkspace` that takes an identifier from the caller and goes through the bookkeeping that skips a client's mutation the second time. The first such caller decides.

**Replace the key that seals credentials.** `CREDENTIAL_KEYS` is a comma-separated list of `<version>:<key>`, each key the output of `openssl rand -base64 32`. Add a key with a higher version in front and keep the old one: the new one seals from then on, and the old one goes on opening what it sealed. Remove the old one only when nothing is left that it sealed, which a sealed value says at its start: `1.…` was sealed with version 1. The sealed values are `credentials` in the `channel` table of every workspace, and `registration` in `mastodon_app` and `pending` in `oauth_state` of D1. A key that is removed too early costs a new connection of every channel it sealed. Nothing seals a stored value again by itself yet: `PLAN.md` section 16 says where that belongs.

**Add a binding or variable.** Edit `apps/worker/wrangler.jsonc`, then run `pnpm typecheck`. It runs `wrangler types`, which regenerates the git-ignored `worker-configuration.d.ts` that declares `Env` and the runtime types. `pnpm install` generates it too. A secret is not in `wrangler.jsonc`: declare it in `Secrets` in `apps/worker/src/env.ts`, as optional, and add it to `.dev.vars.example`. Routes take their bindings from the `Bindings` type there, not from `Env`, which differs between machines with and without a `.dev.vars`.

**Add a simulator** of a service that is not a social network. Add a directory to `packages/simulators/src` and an entry to `exports` in its `package.json`. A simulator answers on the real addresses of the service, as a function with the signature of `fetch` that fails for every other host. It is written from the documentation of the service, rejects what the service rejects, takes its clock as a parameter, and has tests of its own. `src/google` is the example.

**Add a network.** `PLAN.md` section 6 says how each network maps onto the contract. Check that against the network's documentation first, and change the contract, with the plan, if it does not hold. Then, in this order, with the Worker last:

1. The limits. In `packages/core/src/network/limits.ts`, add a schema for what an account of the network may post to `limitsSchema`, and the network's way of counting to `countCharacters`. `validateContent` is what the browser and the Worker check content with, so a rule of the network that it does not have yet goes there.
2. The simulator, in `packages/simulators/src/<network>`, with an entry in `exports`. `src/mastodon` is the example:
   - It is `create<Network>Simulator(world)` and returns a `fetch` that answers on the network's real hosts and throws a `TypeError` for every other host.
   - It keeps everything in the world and nothing in itself: accounts, tokens and posts in the world's own tables, with more fields if it needs them, the rest in `world.table("<network>", ...)`. It makes its secrets with `simulatedSecret` or `world.issueToken`, and looks tokens up with `world.findToken`, which finds nothing that the world did not issue.
   - It is written from the network's documentation and enforces the network's rules itself: authentication, scopes, validation of every parameter, the counting of characters, what makes a repeated request safe, the bodies and statuses of errors, the rate limits. It keeps and hands out what the network would, which is not always what it was sent: Mastodon rewrites the mentions in a status. It imports nothing from `@pigy/providers` or `packages/core/src/network`. Refuse what is not simulated, do not ignore it. Mark what you had to assume with `GUESS` in a comment.
   - It takes its faults from `world.faults.take` with the kinds its network can suffer from, and declares them, with the kinds of request they can strike, as Mastodon's `mastodonFaultKinds` and `mastodonOperations`. A kind that the world does not have yet, such as a token that expires, is added to `faultKinds` in `world/faults.ts` in the same change, with a test that shows the simulator applying it. The same goes for what a token or a post of the world lacks, such as a time at which a token ends.
   - Its consent page is `consentPage` of `world/pages.ts`, served for `GET` on the network's authorization address and answered with a `POST` to the same address, which carries `account` or `action=deny`. That is what lets `answerConsent` work for every network.
   - It has tests of its own for the rules it enforces.
3. The adapter, in `packages/providers/src/<network>`, with an entry in `exports`: a function that takes `fetch`, the clock and what is the network's own, and returns a `Provider`. It sends requests with `send` of `src/http.ts`, checks every answer and everything that comes back from storage with a Zod schema, and fails with `ProviderError` only. The comments in `src/provider.ts` are the contract. What an adapter gets wrong most easily:
   - `publishStep` makes at most one request that changes something, and a step can be run again at any time, a moment or days later, with the same request. It must not publish a part twice then, and it must not count on what the network remembers for a while. So before a request that publishes, the progress has to hold what a later run needs to find out whether the request was carried out, and a step that does not find it there returns it and sends nothing. `PLAN.md` section 8 has what that is for each network. Where the network offers nothing, a request to publish that ends without a clear answer fails with `uncertain`, never with `retry`.
   - A step that looks for what an earlier run has published compares with what the network keeps, which is not always what was sent. It takes a post for its own only if the post is the same in everything that the step sends: the text, the place, who sees it, and what it has besides its text. It looks at nothing from before the delivery, whatever the network lists. And it counts on the caller to run the deliveries to one account one after the other, which the contract of `publishStep` requires: two that begin together with the same first part cannot be told apart.
   - The progress, the adapter's notes in `state` included, is stored as it is. No secret goes into it.
   - `completeConnect` fails with `fail` whatever went wrong. The code of a callback is good once, so there is nothing to try again. What a callback says about a failure is quoted like the answer of a network, with `quotable`: without the secrets that `pending` holds and without the code of the callback. Anybody can send a browser to the callback address, and the message is logged.
   - An adapter that has `refresh` fails with `refresh` when the network refuses credentials that a refresh would cure, whatever the time it has named in `refreshAt`. It fails with `reconnect` only when a refresh would not help.
4. The conformance suite. Add `packages/providers/test/conformance/<network>.test.ts`, which describes the network as a `Harness` and passes it to `describeProvider`, twice: with a simulation, and with the harness of a live run. Add `test/live/<network>.live.ts` and the names of its environment variables to `scripts/conformance-live.mjs`. What the suite does not cover because it is the network's own goes into tests next to the adapter. Some branches of `spec.ts` have never run, because no network so far takes them: a refresh, an access that ends, a network that cannot revoke, a thread that is joined into one post, `uncertain`. Each says so in a comment. The first network that takes one has to show that the branch can fail: break the adapter on purpose, see the test fail, and remove the comment.
5. One live run, to confirm that the simulator and the network agree. Where they do not, fix the simulator.
6. The Worker. Connecting, disconnecting and the routes are the same for every network, so this is what a network adds:
   - An entry in `adapters` in `apps/worker/src/network/providers.ts`, which makes the adapter from the reach of a workspace. What the adapter takes besides `fetch` and the clock comes from there: a registration of the operator's from secrets of the Worker, declared as in "Add a binding or variable", or a store, as `mastodon-apps.ts` is for Mastodon. A store that holds a secret seals it.
   - Its simulator in `request` of `apps/worker/src/sim/object.ts`, next to Mastodon's: the simulator that has the host of a request answers it. Give a new world accounts of the network where it is seeded. A world that exists is not seeded again, so decide what the worlds from before get.
   - The path of its consent page in `worldPage` of `apps/worker/src/sim/world.ts`. Nothing else of a simulated network is served to a browser.
   - The callback address `https://<host>/connect/<network>/callback`, wherever the network wants it registered. `connectCallbackPath` in `packages/core` makes the path.
   - If its accounts are found by something a person types, say in `packages/core/src/connect.ts` what `identifier` is for it, and add what a sandbox offers to `packages/core/src/sandbox.ts`.
   - Tests: the whole connection in a sandbox and in a live workspace, in `apps/worker/test`, with the network's simulator added to `network` in `test/helpers.ts`.

**Run the conformance suite against a real network.** This posts to a real account. Use an account that is there for the purpose.

For Mastodon, sign in to the test account on its instance, open Preferences, Development, New application, and create one with the scopes `profile` (`read:accounts` before Mastodon 4.3), `read:statuses`, `write:statuses` and `write:media`. - It runs `test/conformance/spec.ts` against the server, without the tests that take a simulation: consenting, arming a fault, moving the clock.

**Add a test.**

- `packages/core`, `packages/providers` and `packages/simulators`: `src/**/*.test.ts` next to the code. Runs in Node, so a test may import Node modules, which the code under test may not. `test/setup.ts` makes the global `fetch` throw.

To test what an adapter does with an answer that the network would not give, wrap the simulator's `fetch` and answer in its place, as `setup` in `packages/providers/src/mastodon/mastodon.test.ts` does.
- `packages/providers`: what every adapter must do goes into `test/conformance/spec.ts`, once, for all networks. What is one adapter's own goes next to it. The specification marks with `skip` what a live run cannot do.
- The sync client in `packages/core`: `test/sync-browser.ts` is a browser for it. `browser()` has one stored copy, `tab()` opens a store over it and `holder()` one that holds the socket. The test plays the server: `socket.send(patch({ … }))`, `socket.close(code)`, and `socket.sent` and `socket.mutates` are what the client has said. `advance(ms)` moves the clock and runs what was scheduled. Nothing waits for real time. `storage` and `tabs` are the stored copy and the channel between the tabs, for what a test does in place of a tab that it has no store for: one that died before it told the others of a write or after it said that it could not store one, or one that runs the next version of the app. `network.access` is what the server says when it is asked why a handshake failed, and `"silent"` leaves the question open.

To make an object fail at a point of the test's choosing, spy on a method of `WorkspaceStore.prototype` with `vi.spyOn`: the objects run in the isolate of the test and share its modules. Pass only the time that the one thing takes which the test waits for: nothing is awaited in between, so an hour would also run every ping without its answer. `synced(store)` waits until the store follows the server, and `shown(store)` is its view in the form of `SyncClient.copy`. Use these tests for what the client and the object do together, and `packages/core` for what the client does with one message.

The tests in `network-guard.spec.ts` are expected to fail, so the list reporter marks them with a cross in a run that passes.
- Synced data in `e2e`. It routes the sync socket and the API and leaves the page itself alone, because until phase 2c the app does not load without a server: `context.setOffline` would break the reload that such a test is about. A session that ends behind the back of the app, by a request of the test or by what somebody else does, is a trap for a test: the app hears of it by itself, the next time its socket fails or a moment after a navigation, and leaves for the sign-in page in the middle of whatever the test does in that window then. A `goto` that this falls into fails, waits for ever or ends on the app's page, so taking it again does not help. Before the session ends, cut the page off, API included, or close it, and take the next step in a new window: the two tests of a session that ends in `sync-drafts.spec.ts` and the removal in `access.spec.ts` show how. Where the app in the new window still believes in the session, it leaves for the sign-in page with a page load of its own, so `goto` waits for `commit` there and the test for the address. Between `hold()` and `release()` it keeps the changes of the page from the server and lets everything else pass, which makes a moment last that is otherwise over at once: the page has heard of a change from elsewhere and its own is not confirmed. `breakStorage(page)` makes the writes to IndexedDB fail, in that tab alone. To test what the app does only every so often, or what is on screen only for so long, stop the clock of the page with `page.clock` and move it by hand, as the tests of the session check and of the two notices in `drafts.spec.ts` do. A notice is put on screen and taken off it by timers of the notice library, so the clock has to be moved for those too. A device whose clock is behind the server's is `page.clock.install` with an earlier time and nothing else, which leaves the clock running: `sync-drafts.spec.ts` has a draft keep its place in the list on one. A test that says that the app did not open a socket or send a request needs something to have happened after the moment at which it would have: the too-old window in `sync-drafts.spec.ts` shows how. Three things to know: a routed WebSocket does not raise the page's `websocket` event, so count sockets in the route. A new draft with text is two changes, the draft and its text. And `restore()` tells the page that the network is back, as a browser does, so that the test does not wait out a pause.

What is left is a live workspace, which talks to the real networks: in the e2e build, `outboundFetch` in `apps/worker/src/outbound.ts` gives the app a `fetch` that answers every request itself, with a 502. `connect.spec.ts` proves it, with a host under `.invalid`. ## Deployment

Deployment is set up in phase 11. Until then nothing is deployed. What the code already relies on:

- `wrangler.jsonc` binds two Durable Object classes, `WorkspaceDO` as `WORKSPACE` and `SimWorldDO` as `SIM_WORLD`, and declares them in `migrations` with `new_sqlite_classes`, in the entries `v1` and `v2`. The first `wrangler deploy` creates both classes with SQLite storage: nothing to set up beforehand. The entries must be right before that deploy, because the storage of a class cannot be changed afterwards, and an entry that has been deployed is never edited. Adding, renaming or deleting a class takes a new entry with a new tag.
- The databases of the workspaces need no step in a deploy. Their migrations are part of the Worker: the build puts each SQL file next to `index.js` as a module of its own, which `wrangler deploy` uploads with it.
- A deploy can close the sync sockets, and clients connect again by themselves. It can also leave a socket open under the new code. If the deploy raised `syncProtocolVersion` or `syncSchemaVersion`, the object closes such a socket the next time it is used, and clients that still run the old app are turned away until they have loaded the new one. A window of the old app then says "Reload to update" in its sync indicator, stops connecting and leaves the socket to a window that runs the new one. So does a window of the old app when another window has loaded the new one and brought the local copy to its schema. What is written in it meanwhile stays in the local copy and is sent after the reload.
- The D1 database has no `database_id` in `wrangler.jsonc`. The first `wrangler deploy` creates a database named `pigy` and binds it, and later deploys keep the binding. Wrangler 4.162 does this by default. Migrations are applied to it with `wrangler d1 migrations apply DB --remote`.
- The Worker needs four secrets: `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `ADMIN_EMAILS` and `CREDENTIAL_KEYS`. Without the first two nobody can sign in. The Google client needs the redirect address `https://<host>/api/auth/google/callback`.
- `CREDENTIAL_KEYS` is `1:<key>`, with the output of `openssl rand -base64 32` as the key: `wrangler secret put CREDENTIAL_KEYS`. Without it no account can be connected, in a sandbox no more than for real. Keep a copy of it somewhere safe: the credentials of every channel are worthless without it. "Replace the key that seals credentials" above says how it is changed.
- Connecting accounts needs nothing else. The networks send the browser back to `https://<host>/connect/<network>/callback`, a path that `assets.run_worker_first` sends to the Worker. Mastodon needs no registration by hand: pigy registers itself with each instance, with that address, the first time somebody connects an account there.
- Always deploy right after `pnpm build`, never after `pnpm preview:e2e` or `pnpm e2e`. Each build points `wrangler deploy` at itself, through `apps/web/.wrangler/deploy/config.json`, and the e2e build contains the simulated sign-in.
