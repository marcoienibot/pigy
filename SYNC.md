# pigy sync protocol

How a client keeps a copy of a workspace and changes it. Protocol version 2, schema version 8.

This document is the contract between the server and any client: the browser store of the app, or anything else. It is meant to be enough to write a client from. The message schemas, the row schemas, the mutators, the limits and the versions are code in `packages/core/src/sync`, and a client should use them rather than copy them. The server is `apps/worker/src/workspace`. `apps/worker/test/sync-client.ts` is a small client written from this document, which the tests of the server use. The client of the app is `packages/core/src/sync/client`, and what it takes from a browser is in `apps/web/src/sync`.

## 1. Model

- A **workspace** is one user's data in one environment. Everybody has two, `live` and `sandbox`. `GET /api/workspaces` lists them, as `{ "workspaces": [{ "id": "…", "environment": "live" }, { "id": "…", "environment": "sandbox" }] }`, and creates them the first time.
- The **synced tables** of a workspace are the part of it that clients hold a copy of: `post`, `post_part`, `channel`, `post_target`, `target_part_result`, `notification`, `schedule_slot` and `settings` so far. `packages/core/src/sync/tables.ts` describes their rows. A row has an `id`, a UUID version 7 in lowercase, that is unique in its table.
- A client never writes rows. It sends **mutations**: the name of a mutator and its arguments, such as `post.create`. The server runs the mutator, and what it does to the rows is what counts. A client may run the same mutator, from `packages/core/src/sync/mutators.ts`, on its own copy first, to show the change before the server has answered.
- The server applies mutations one at a time, in the order they arrive. Each mutation that changes something is one change and gets a **sequence number**: the changes of a workspace are numbered 1, 2, 3 and so on. A **cursor** is a sequence number, and a client whose cursor is N has exactly the rows that the server had after change N. Cursor 0 is the empty workspace.
- A **client** is one local copy: its rows, its cursor, the mutations it has made that the server has not confirmed, and the ID of the last one that the server has confirmed. It has a **client ID**, a UUID version 7 that it makes up once, and it numbers its mutations 1, 2, 3 and so on. The server remembers the last mutation it has processed for each client ID, which is what makes it safe to send a mutation twice. A client keeps its copy and its client ID for one workspace: another workspace is another copy with another ID.
- A client has **at most one socket** open. Tabs of a browser that share a stored copy, and with it a client ID, choose one among them to hold the socket and to pass on what it receives. Or each tab keeps a copy of its own, with a client ID of its own. Two sockets with one client ID do not work: every patch moves the cursor that both go by, so each would find that the other has made it miss a patch, and the answer to a `mutate` goes only to the socket that sent it. The server therefore keeps one socket per client ID, the one that was opened last, and closes the others when they have said hello.
- A client that loses its local copy, or any part of it, **starts over**: it makes up a new client ID and says hello with the cursor `null` and the `lastMutationId` 0, as a client that has nothing. With the old ID, the server would take the mutations of a second copy for repeats of the first one's, and skip them. Two things tell a client that it has to start over:
  - It is told of a `lastMutationId` higher than any mutation it has made. It has no unconfirmed mutations left then: the patch that said so took them all for confirmed.
  - The server answers a `mutate` with the error `mutation_gap`, and when the client has connected again, it does not have the mutation that the server expects, which is the one after the `lastMutationId` of the answer to its hello. Either the client has lost that mutation, or the server has gone back to an earlier state. The client keeps the unconfirmed mutations that it has. Their IDs are all higher than that `lastMutationId`, so the server has processed none of them, and sending them under the new client ID cannot apply one twice. The client numbers them again from 1, in the order they were made. Those that build on a mutation that is missing are rejected, like any mutation that cannot be applied.

## 2. Connecting

A client opens a WebSocket to `/sync/<workspace ID>` on the origin of the app: `wss://<host>/sync/<workspace ID>`. The handshake is an ordinary request to the Worker, which lets it through if

- it comes from a page of the app itself: the `Origin` header is the origin of the address. A browser sends the session cookie with a handshake that any site starts, so this is what keeps other sites out. Otherwise 403.
- the session cookie is that of a signed-in user. Otherwise 401.
- the workspace belongs to that user. Otherwise 404, the same as for a workspace that does not exist.
- the workspace has fewer than 32 sockets open. Otherwise 429.

A request that is not a WebSocket handshake gets 426. A browser does not tell a script why a handshake failed, only that it did. A client whose handshake fails therefore asks `GET /api/workspaces`: a 401 means that it is signed out, and no answer that it is offline. No answer within a time of its choosing counts as none: a network that is up and leads nowhere can leave the request open for minutes. A 200 means that the handshake failed for another reason, such as too many sockets or a failure of the server. The client then tries the handshake again after a pause, which it makes longer every time the handshake fails. If the 200 does not list the workspace, the workspace is not the user's, and trying again is no use.

The session is checked at the handshake and not again. To make up for that, a socket lasts five minutes. After that the server closes it with the code 4401, when the next message arrives on it or the next change would be sent to it. An idle socket stays open and costs nothing. A client that is closed with 4401 connects again at once, and that handshake checks the session again. So somebody who signed out, or whose invitation was withdrawn, can read and write through a socket that was open at the time for at most five minutes. A message that arrives on a socket that is past its time is not processed. The server can end a socket with 4401 before the five minutes are over, in the same way: section 4 has the one case.

## 3. Messages

Every message is one text frame with one JSON object, which has a `type`. A field that is not described here makes a message invalid, in both directions.

### Client to server

**`hello`** is the first message on every socket, and is sent once.

```json
{ "type": "hello", "protocolVersion": 2, "schemaVersion": 8, "clientId": "0192…", "cursor": 42, "lastMutationId": 7 }
```

`cursor` is the `to` of the last patch that the client has applied, or `null` if it has applied no patch. `lastMutationId` is the `lastMutationId` of the last patch that the client has applied, or 0 if it has applied no patch. It says that the client knows what became of its mutations up to that one, and the server forgets what it kept to tell the client: see section 4.

The server answers with a patch that brings the client up to date, and from then on sends it every change. A socket that has not said hello receives nothing. Of the sockets that have said hello with one client ID, the server keeps the one that was opened last and closes the others with the code 4409. That is usually an older socket that is still open. It is the socket of this hello, which then gets no answer, if the hello arrives after that of a socket that was opened later: a hello can be held up on its way past the point at which the client gave the socket up.

**`mutate`** carries mutations of the client, at least one and at most 100.

```json
{ "type": "mutate", "mutations": [{ "id": 7, "name": "part.setText", "args": { "id": "0192…", "text": "Hello" } }] }
```

The IDs in a message increase by one. The server skips the mutations that it has processed before, and runs the others in order. If the first mutation is not the one after the last that was processed, or an earlier one, the server runs none: it answers with the error `mutation_gap` and closes the socket. Each `mutate` is answered with one patch, also if it changed nothing.

**`ping`** is answered with `{ "type": "pong" }`. It is there for a client to find out that a socket is dead. Sent as exactly the text `{"type":"ping"}`, which is `pingMessageText`, it is answered without waking the workspace up, at any time, also before the hello.

A message is at most 262,144 characters long, counted the way `String.length` counts. A client with more mutations than fit sends several messages.

### Server to client

**`patch`** takes the client from one cursor to another.

```json
{
  "type": "patch",
  "from": 42,
  "to": 44,
  "changes": [
    { "op": "put", "table": "post_part", "row": { "id": "0192…", "postId": "0192…", "targetId": null, "position": 0, "text": "Hello" } },
    { "op": "delete", "table": "post", "id": "0192…" }
  ],
  "more": false,
  "lastMutationId": 7,
  "rejected": [{ "id": 6, "code": "not_a_draft", "message": "Only a draft can be edited" }]
}
```

- `from` is the cursor that the patch applies to, and `to` the cursor of a client that has applied it. `from` is `null` for a **snapshot**: the client first forgets every row it has.
- `changes` has each row at most once. `put` carries the whole row as it is at `to`, and replaces the row with the same ID or adds it. `delete` removes the row with that ID, if the client has it. The order of the changes means nothing.
- A patch can be more than one message. All but the last have `more: true`, they follow each other with nothing in between, and they differ only in `changes` and `more`. A message of the server holds at most about 524,288 characters of changes.
- `lastMutationId` is the ID of the last mutation of the receiving client that the server has processed, 0 if there is none.
- `rejected` lists the mutations of the receiving client that were rejected, with the reason: those with an ID after the `lastMutationId` that the client had before the patch, and up to the `lastMutationId` of the patch. What the client had before is what the patch before said on the same socket, or the hello, for the answer to a hello. A rejected mutation had no effect and counts as processed.

A client applies a patch as one step, when its last message is in:

1. If `from` is `null`, drop all rows. If it is a number other than the client's cursor, the client has missed a patch: it closes the socket and connects again.
2. Apply the changes.
3. Set the cursor to `to`.
4. Drop the unconfirmed mutations with an ID up to `lastMutationId`, take note of the ones in `rejected` for the user, and keep `lastMutationId` for the next hello. An entry of `rejected` whose ID is not above the `lastMutationId` that the client has stored is skipped: the client has taken note of that one before. This can only happen where tabs share a copy: the tab that takes the socket over says hello with what was stored at the time, and the tab that held the socket before can store one more patch after that. The `lastMutationId` of a patch is stored as it is, also when it is lower than the stored one, which means that the server has gone back to an earlier state: section 1 says how the client finds out and starts over.
5. If mutations were shown before they were confirmed: run the unconfirmed mutations that are left on top of the new rows, for display.

Steps 1 to 4 belong in one transaction of the local store: the rows, the cursor, the `lastMutationId`, the unconfirmed mutations that go, and what the client keeps of each rejection until the user has been told. Two things depend on it. The patch that confirms a mutation is the patch that carries its changes, so there is no moment at which the client has neither its own version of a change nor the server's. And the server forgets a rejection as soon as a hello has a `lastMutationId` that covers it. A client that stored the `lastMutationId` of a patch without its rejections, and was stopped in between, would drop the mutations and never learn that they were rejected.

**`error`** says what the client did wrong. The server then closes the socket with the code 4400.

```json
{ "type": "error", "code": "version_mismatch", "message": "…", "protocolVersion": 2, "schemaVersion": 8 }
```

`protocolVersion` and `schemaVersion` are what the server speaks. The codes:

| Code | Meaning | What a client does |
| --- | --- | --- |
| `version_mismatch` | The `hello` had another protocol or schema version, or the server changed to another one while the socket was open | If the server's versions are higher, the client is out of date: it updates itself, which for the app means loading the new version of itself, and does not connect before. If they are lower, the server is in the middle of an update: try again later |
| `invalid_message` | Not JSON text, not a message of the protocol, a second `hello`, or a `mutate` before the `hello` | A bug in the client |
| `message_too_large` | Longer than the limit | A bug in the client |
| `mutation_gap` | See `mutate` | Connect again: the answer to the hello says which mutation the server expects next, the one after its `lastMutationId`. A client that does not have that mutation, because it lost it or because the server has gone back to an earlier state, would get the same error every time. It starts over: see section 1 |

**`pong`** answers a `ping`.

### How the server closes a socket

| Code | Meaning | What a client does |
| --- | --- | --- |
| 4400 | An `error` message came before | See above |
| 4401 | The socket has reached the end of its life. A message that was arriving is not processed | Connect again at once |
| 4409 | Another socket with the same client ID, one that was opened later, has said hello | Nothing. The client has a newer socket, and this one is no longer its own. If tabs share the copy, another tab holds the socket now. Connecting again because of this close would close that socket in turn, and so on for ever |
| 1011 | The server failed while it handled a message. It may have processed the message or not. The server also closes the sockets of other clients with this code, when it has made a change and cannot send it to them | Connect again, after a pause |

After any close other than 4400 and 4409, and after a socket was lost, a client connects again, says hello with its cursor and its `lastMutationId`, and sends its unconfirmed mutations again under the IDs they have: all of them, or those after the `lastMutationId` of the answer to its hello. The server skips the ones that it has processed, so a client never has to know whether a message got through, after a 1011 no more than after a lost socket. A client that pauses longer after every failure does not start from the short pause again because a hello was answered. When the database of a workspace is full, the server answers every hello and fails on the `mutate` that follows, every time: the failures are over when a `mutate` has been answered, or when a socket has lasted for a while. A socket can be lost without the client being told. A client that gets no `pong`, or no patch in answer to a `mutate`, within a time of its choosing closes the socket and connects again. After 4400 a client does what the table of errors says for the error that came before, which for some of them is not to connect again. After 4409 it does nothing.

## 4. Mutations

The mutators, their arguments and what they refuse are in `packages/core/src/sync/mutators.ts`. For now:

| Name | Arguments | Does |
| --- | --- | --- |
| `post.create` | `id`, `partId`, `text` | Creates a draft with its first part. Rejected with `already_exists` if either ID is taken |
| `part.setText` | `id`, `text` | Replaces the text of a part. Rejected with `not_found` if the part is gone, with `not_a_draft` if its post is past being a draft |
| `part.add` | `id`, `postId`, `channelId`, `afterId`, `text`, and optionally `mustFollow` | Adds a part to a text of a draft: to the post's own for the `channelId` null, otherwise to the text that is written for that account. It goes after the part `afterId`, first for null, and to the end if that part is gone or not of this text. With `mustFollow` true it goes after the part `afterId` or nowhere: it is rejected with `not_found` if that part is gone or not of this text. `mustFollow` says nothing for the `afterId` null. Rejected with `not_found` if the post is gone, and for a `channelId` if the post does not go to that channel, or no longer, or if the account has no text of its own: a part for an account never goes into another text. Rejected with `not_a_draft` if the post is past being a draft, with `already_exists` if the ID is taken, with `too_many_parts` if the text has 100 parts |
| `part.remove` | `id` | Removes a part from its text, the post's own or the one of an account. Does nothing if the part is gone. Rejected with `not_a_draft` if its post is past being a draft, and with `last_part` if it is the only part of its text |
| `part.move` | `id`, `afterId` | Moves a part within its text, to after the part `afterId`, or to the beginning for null. Does nothing if that part is gone, not of this text or the part itself, or if the part is there already. Rejected with `not_found` if the part is gone, with `not_a_draft` if its post is past being a draft |
| `post.delete` | `id` | Deletes a post with its parts, those that are written for single accounts included, its targets and their results. Does nothing if the post is gone. Rejected with `sending` while the post is being sent. With `ifTrashed` true it deletes only a post that was put aside, and does nothing to any other: "Scheduling" below |
| `target.add` | `id`, `postId`, `channelId` | Chooses a channel for a draft to go to: adds a target with the status `pending`. Does nothing if the draft goes there already. Rejected with `not_found` if the post or the channel is gone, with `not_a_draft` if the post is past being a draft, with `already_exists` if the ID is taken |
| `target.remove` | `postId`, `channelId` | Takes a channel back from a draft, with the text that was written for it. Does nothing if the draft does not go there. Rejected with `not_found` if the post is gone, with `not_a_draft` if it is past being a draft |
| `target.customize` | `postId`, `channelId`, `parts` | Gives an account of a draft a text of its own: `parts`, each an `id` and a `text`, in this order, at least one, at most 100, and at most 40,000 characters together. Does nothing if the account has one already, whatever `parts` says. Rejected with `not_found` if the post is gone or does not go to the channel, with `not_a_draft` if the post is past being a draft, with `already_exists` if an ID is taken or named twice: nothing of the text is stored then |
| `target.followPost` | `postId`, `channelId` | Removes the text that was written for an account: it gets the post's again. Does nothing if it does so already, or if the post does not go to that channel. Rejected with `not_found` if the post is gone, with `not_a_draft` if it is past being a draft |
| `post.publish` | `id` | Asks for a post to be sent to its channels now: a draft, or one that is scheduled, which leaves the queue if it was in it. Rejected with `not_found` if the post is gone, with `not_a_draft` if it has gone out, with `no_channels` if it has no target |
| `post.schedule` | `id`, `dueAt` | Gives a draft, or a post that is scheduled already, the time `dueAt` to go out at, in milliseconds since the Unix epoch: the post is `scheduled`, with the `mode` `custom`. A time that has passed is taken, and the post is taken up at once: "Scheduling" below. Rejected with `not_found`, `not_a_draft` and `no_channels` as `post.publish` is, and with `too_many_scheduled` if the post is a draft and the workspace has 500 scheduled posts |
| `post.enqueue` | `id`, `first` | Puts a draft, or a post that is scheduled for a time, into the queue: at its end, or at its front with `first`. The post is `scheduled`, with the `mode` `queue`. A post that is in the queue stays where it is, or moves to the front with `first`. Rejected as `post.schedule` is |
| `post.move` | `id`, `afterId` | Moves a post within the queue, to after the post `afterId`, or to the front for null. Does nothing if that post is not in the queue, or if the post is there already. Rejected with `not_found` if the post is gone, with `not_scheduled` if it is not in the queue |
| `post.unschedule` | `id` | Takes a scheduled post back to the drafts. Does nothing to a draft. Rejected with `not_found` if the post is gone, with `not_scheduled` if it has gone out |
| `post.trash` | `id` | Puts a scheduled post aside, with the time as its `trashedAt`: the first step of deleting it, which `post.restore` takes back. The post is as good as gone from then on: "Scheduling" below. Does nothing if the post is gone or put aside already. Rejected with `not_scheduled` if the post is not `scheduled`: it has gone out, or is a draft again |
| `post.restore` | `id` | Takes back that a post was put aside: it is scheduled again as it was, at its time or at its place in the queue. Does nothing if the post is gone or is not put aside. Never rejected: "Scheduling" below has what becomes of a post that cannot be scheduled as it was |
| `slot.add` | `id`, `weekday`, `minute` | Adds a slot to the queue: `weekday` from 0 for Sunday to 6, `minute` from 0 to 1439 after midnight. Does nothing if the workspace has a slot at that time of the week. Rejected with `already_exists` if the ID is taken, with `too_many_slots` if the workspace has 200 |
| `slot.remove` | `id` | Removes a slot. Does nothing if it is gone |
| `queue.setPaused` | `paused` | Pauses the queue, or lets it go on. Does nothing if it is so already |
| `settings.setTimeZone` | `timeZone`, and optionally `onlyIfUnset` | Sets the time zone of the workspace, an IANA name. With `onlyIfUnset` true it does nothing for a workspace that has one. Rejected with `invalid_arguments` for a zone that the server does not know |
| `target.retry` | `id` | Asks for a delivery that failed to be tried again. Rejected with `not_found` if the target or its channel is gone, with `not_failed` unless the target is in `error` or `uncertain` |
| `notification.read` | `notifications`: 1 to 100 of `{ id, createdAt }` | Marks notifications of the inbox as read. Each is named as the device saw it, with its `createdAt`. One that is gone, read already, or has another `createdAt` by now is left as it is |
| `notification.dismiss` | `id`, `createdAt` | Takes a notification out of the inbox, named as the device saw it. Does nothing if it is gone or has another `createdAt` by now |

Whoever creates a row makes up its ID, so a client can create rows while it is offline. `uuidv7` in `packages/core` makes one.

Some mutators are the server's own. A client that sends one has it rejected with `not_allowed`, like any mutation that cannot be applied, and a client does not run them on its copy either: it receives what they did in a patch.

| Name | Does |
| --- | --- |
| `channel.connect` | Stores an account that was just connected as a channel with the status `connected`. An account that has a channel keeps it, under the ID it had |
| `channel.setLimits` | Replaces what the account of a channel may post, when its network has been asked again |
| `channel.renew` | Stores when the access of a channel ends, after the server has renewed its credentials |
| `channel.lapse` | Marks a channel as `needs_reconnect` when its network would not renew its access. It names the connection that was refused by the `connectedAt` of the channel, and does nothing if the channel has another connection by now or is gone |
| `channel.disconnect` | Removes a channel. Does nothing if the channel is gone. Its targets go the way "Publishing" below says |
| `post.due` | Takes up a scheduled post whose time has come: sends it, holds it or gives it the next slot. "Scheduling" below |
| `target.start` | Begins the delivery of a target that waited its turn: `sending`, in a new attempt |
| `target.progress` | Adds the results of the parts that a delivery has published |
| `target.end` | Ends a delivery as `sent`, `error` or `uncertain`. It names the connection whose access the network refused, if it refused one, by the `connectedAt` of the channel, and marks the channel as `needs_reconnect` if that is the connection which the channel still has |
| `channel.warnOfExpiry` | Adds the notification that the access of a channel ends within a week. Does nothing for an access that does not end within a week, has ended, or is of a channel that needs connecting again |
| `notification.prune` | Removes the notifications that it names: the server runs it for those that are older than 30 days |

They are the server's because a channel stands for something that only the server has: the credentials of the account. A channel that a client made up would have none, and one that a client dropped would leave them behind, still good at the network. So an account is connected and disconnected over HTTP, through the routes that `packages/core/src/connect.ts` describes, and a client learns of the outcome as it learns of every change.

### Threads, and the text of one account

A post has a text of its own, which is one or more rows of `post_part` whose `targetId` is null: more than one is a thread. The parts are read in ascending order of `position`, then of `id`.

- **The order is kept by the server, and a mutation names a part, not a position.** `part.add` and `part.move` say which part the part goes after. The mutator finds that part in the rows as they are when it runs, puts the part behind it, and numbers the parts of the text anew, from 0 and without a gap: it writes the rows whose `position` has changed. So a client never computes a position, and two devices that edit a thread at once cannot leave two parts in one place or a part in none. Two parts that are added after the same part both stay, the one that reached the server later nearer to that part. A part that is added after one that another device has removed goes to the end of the text, with what was typed into it, unless it says `mustFollow`: then it is rejected with `not_found`. That is for a part which continues a text of the client's own making and belongs in no other, see below. A part that is moved to after one that is gone stays where it is. A client that shows a mutation before it is confirmed runs the same mutator on its copy, and the patch that confirms it brings the positions as the server has them.
- **A text has one part at least and 100 at most.** `part.remove` is rejected for the only part of a text with `last_part`, and `part.add` for a text that is full with `too_many_parts`.
- **An account can get another text than the post's.** The rows of `post_part` whose `targetId` names a target are the text that this target gets in place of the post's own: a thread of its own, with its own number of parts, numbered from 0 by itself. A target that no part names gets the post's text. `target.customize` writes such a text as a whole, which a client fills with the post's text as it is, for the person to change. It comes in one mutation so that an account never has half a text, and so that of two devices that begin one for the same account, the first wins as a whole. Because one mutation has to fit one message, it carries at most 40,000 characters. A client that brings back a longer text, which an account can have once its text has grown part by part, sends the first parts with `target.customize` and each part after them with `part.add`, after the part before it and with `mustFollow`: `ownTextMutations` in `packages/core` makes these. The steps are not one, and still no account gets a text of two halves. If the account has a text by the time they arrive, because another device gave it one or the person did so since, the `target.customize` does nothing, and each `part.add` names a part that this text does not have: it is rejected, and nothing of the text that was brought back is put behind the other one. A client that offers to bring a text back does not do so for an account that has a text on its copy. No mutation is longer than a message may be if its arguments are what its mutator takes, also when JSON writes every character as six, and a client makes no other: a mutation that does not fit would never leave its outbox, and nothing behind it would. From then on the parts of that text are edited with the mutators of every part: `part.setText`, `part.remove` and `part.move` by the ID of the part, and `part.add` with the `channelId` of the account. `target.followPost` removes the text. So do `target.remove`, the disconnect of the channel while the post is a draft, and `post.delete`. A device that was in the middle of such a text when another took it away has its mutations rejected with `not_found`: `part.add` because the account has no text any more, or no target, and `part.setText` and `part.move` because their part is gone. Nothing of it reaches the post's own text.
- **An account is named by its channel.** `target.customize`, `target.followPost` and `part.add` name the post and the channel, like `target.remove`, and not the target: of two devices that chose the channel, one has made up an ID for the target that the server never took.
- **What a delivery publishes** is the text of its target: the parts that name it, or the post's own. The rows of `target_part_result` name those parts in `partId`. None of it changes once the post is published: every mutator above is rejected with `not_a_draft` then, so an attempt that is tried again goes on with the text that the first one began with.

### Channels

A row of `channel` is a connected account: its network, the network's ID of the account, the handle, the name, the addresses of its picture and of its page, the status, when it was connected, when its access ends, and what the account may post. A workspace has at most one channel per network and account. The credentials are no part of the row. They are in a column that is not synced, and no message carries them.

- `status` is `connected`, or `needs_reconnect` once the network has refused the access of the channel: to a delivery, or to the server when it went to renew the access by itself, which it does on the networks that have that, whether or not anybody posts. Connecting the account again brings the channel back to `connected`, under the same ID.
- `avatarUrl` and `profileUrl` are HTTPS addresses that a browser can open, or null. They are null for every account of a simulated network, which has no addresses.
- `expiresAt` is null on the networks whose access does not end, such as Mastodon, and on those that do not say when it ends, such as Bluesky. On LinkedIn it is 60 days after the account was connected, and nothing renews the access: the account is connected again. On Threads it is 60 days after the access was last renewed, which the server does by itself about a week after the time before: `channel.renew` moves it each time, and a client has nothing to tell a person of an end that is far. An end that is less than two weeks away is one that the server has not been able to put off for weeks: the app says the day then, while the person can still connect the account again. It passes only where the server could not renew in all those weeks.
- `limits` is what the account may post, as its network said at `limitsCheckedAt`: the object that `validateContent` in `packages/core` checks content against, which names its network. Each network has limits of its own form: Mastodon's are read from the instance and count a link as a fixed number of characters, Bluesky's are the same for every account and limit the bytes of a text as well as its characters. LinkedIn's are the same for every account too, and are those of a whole post: a thread is one post there, so `validateContent` also checks that its parts fit together. Threads' are the same for every account, and count an emoji as the bytes that it takes. A client that does not know the form of a network does not count for it. The server asks when the account is connected, and again before it publishes to the channel if the answer is more than a day old. Both are null for a channel whose network has not answered yet. A client that counts characters while somebody types goes by `limits`, and does not refuse what it cannot check: the server checks before it sends.

### Notifications

A row of `notification` is something that the person has to hear of: the inbox of the app lists them, and the server sends a push message for each to the devices that have notifications turned on. A client never adds one. It marks them as read and dismisses them, and both are for every device: the row is the same on all of them.

- `kind` is `post_failed`, `channel_needs_reconnect` or `channel_expiring`. A client that does not know a kind shows the notification in general words.
- There is at most one about a post and one about a channel, and its `id` is the ID of what it is about: of the post, with `postId` set and `channelId` null, or of the channel, the other way round.
- `createdAt` is when what it tells of happened, or happened again. `readAt` is when the person read it, or null.
- What a notification tells of can happen again, which puts a new, unread notification under the same `id`, with a later `createdAt`. So a client that reads or dismisses one says which it saw, with the `createdAt` of the row as it showed it: a device that was offline meanwhile then leaves the newer one alone, which nobody has seen.

When they are added, changed and removed, all of it in the change of the mutator that is named:

| Mutator | What it does to the notifications |
| --- | --- |
| `target.end`, `channel.disconnect` | When the post leaves `sending` with it, which is once per post, when the last of its deliveries has ended, and not once per delivery. If the post is in `error` and one of its deliveries has ended badly by itself since the post last began to be sent: adds the notification of the post, or makes it new and unread if there is one. Otherwise removes the notification of the post, if it has one. See below for which deliveries count |
| `target.end` | When it marks the channel as `needs_reconnect`: adds the notification of the channel, as `channel_needs_reconnect`, in the place of whatever was said of the channel before |
| `channel.lapse` | The same, when it marks the channel as `needs_reconnect` |
| `target.retry` | Removes the notification of the post: the post is on its way again |
| `post.delete` | Removes the notification of the post |
| `channel.connect` | Removes the notification of the channel, when the account had one: connecting again is what it asked for |
| `channel.renew` | Removes the notification of the channel if it is `channel_expiring` |
| `channel.disconnect` | Removes the notification of the channel |
| `channel.warnOfExpiry` | Adds the notification of the channel, as `channel_expiring`. The server runs it once for each end that an access has, a week before that end. An access that the server renews, as that of Threads, has an end that moves with every renewal, weeks before it comes: such an access is told of only when the renewals have not worked for that long |
| `notification.prune` | Removes those that are older than 30 days |

Which deliveries make a notification of a post, when the post leaves `sending` in `error`:

- One that ended as `error` or `uncertain` through `target.end`, and that was asked for when the post last began to be sent or later. A post begins to be sent when it is published, and again when a delivery of it is tried again after all had ended. `queuedAt` of the target says when the delivery was asked for, and `updatedAt` of the post, while it is `sending`, when it began: nothing else changes a post that is sending.
- Not one that ended because the person disconnected its account, which its target says with `disconnected`: the person has done that themselves. A post that is in `error` only for that gets no notification.
- Not one that had failed before the post last began to be sent: the person was told of it then. So a post with two failed deliveries, of which the person tries one again, gets no new notification when that one arrives, though the post is in `error` again for the other.

So a notification is there while what it tells of is unresolved and not older than 30 days, unless the person has dismissed it. A client shows it with what the other tables say of its post or its channel, and leaves one out whose post or channel it does not have.

### Publishing

A post is published to channels. Where it goes is a row of `post_target` for each channel: a **target**, the delivery of the post to that channel. A post has at most one target per channel. What a delivery has published is a row of `target_part_result` for each part: the network's ID of the post that the part is in, and a link to it. The link is null where the network gives none, and for every post of a sandbox: a simulated post has no address that a browser can open. `GET /api/sandbox/feed` shows those, under the same IDs.

A client chooses the channels of a draft with `target.add` and `target.remove`, and asks for the post to be sent with `post.publish`. That is all it does. The server sends, and the client sees the rows change:

1. `post.publish` makes the post `sending` and every target `queued`, with `queuedAt` set. A client that runs the mutator shows this at once.
2. The server begins each delivery when its channel is free: the target is `sending` and its `attempt` is 1. The deliveries to one channel go out one at a time, in the order of `queuedAt`, so a target can stay `queued` while a post that was published before it is on its way to the same account. The targets of one post go to different channels and do not wait for each other.
3. A row of `target_part_result` appears for each part as it is published, the first part first. A thread is seen going out part by part. On a network that makes one post of a thread, which is LinkedIn, the rows of all parts appear together and have the same `remoteId` and the same link: every part is in the one post. The parts are those that the target gets: the ones that were written for it, if there are any, and otherwise the post's own.
4. The delivery ends: the target is `sent`, with `sentAt`, or `error` or `uncertain`, with the reason in `error`, a text for the person. If the network no longer takes the access of the channel, the channel is `needs_reconnect` in the same change. Not if the account was connected again since the delivery read the access that the network refused, so that the `connectedAt` of the channel is no longer that of the connection which was refused: the target fails all the same, and the channel stays `connected`, with an access that the delivery has not tried. A delivery that goes on after the account was connected again reads the new access, and marks the channel if that one is refused.
5. When the last target of the post has ended, the post is `sent` if all of them are, and `error` otherwise. A post whose targets ended differently is in `error`: the targets say which of them arrived.

The statuses of a target:

| Status | Meaning |
| --- | --- |
| `pending` | The channel is chosen and nobody has asked for the post to be sent |
| `queued` | The post is to be sent. The target waits for the server to begin, or for a delivery to the same channel that came before it |
| `sending` | The delivery is under way |
| `sent` | Every part is published |
| `error` | The delivery failed. `error` says why. The parts that were published stay published, and keep their results |
| `uncertain` | The delivery ended and nobody knows how: a part may be on the network without a result. `error` asks the person to look at the account before they try again |

- **What is checked.** Before anything is sent to a channel, the server checks the text that the channel gets, the post's or the one that was written for it, against the `limits` of the channel, with `validateContent`, which also holds the whole text for one channel to 100,000 characters, whatever the network takes. A post that does not pass is not sent there: the target ends in `error` with what is wrong, and the other targets go on. A client can run the same check before it offers to publish.
- **Trying again.** `target.retry` puts a target that is in `error` or `uncertain` back to `queued`, at the end of the queue of its channel, and its post back to `sending`. The next attempt goes on after the parts that have results and does not send those again. A part can also be on the network without a result: it landed, and the server never got the answer. Where the server can look, the next attempt finds such a part and does not send it again. On Bluesky it looks under a key that the delivery recorded, and finds the part whatever has gone to the account since. On LinkedIn the server cannot look at all: a delivery there is `uncertain` whenever a request to post ended without a clear answer, also when a step was interrupted after it had begun to send, and the next attempt sends. For some minutes LinkedIn refuses the same text and names the post that it has, which an attempt after the first then takes for its own. A first attempt that is refused that way has sent nothing before, so the post is not the delivery's: it ends as `error`, with a link to the post that LinkedIn has. On Threads it first asks what became of the part's container, which says whether the part was published, and then finds the post among what the account has posted since the delivery began. A part that Threads says it has published and that is not among those posts is never sent again: the delivery is `uncertain` however often it is tried, with a text that says so. It is `uncertain` too where the server cannot tell whether the part is there, because the account has posted more since than the server reads through. On Mastodon it looks through what the account has posted since the delivery began, so there, and on Threads for the same reason, one thing is in the way: another delivery to the same account that has got as far as asking the network for anything in between, whether or not it posted. Then the attempt starts over, and the first part of the post may be posted twice: the delivery has lost what it had recorded, on Threads the container of its first part too, also one that was published unseen. A delivery that is tried again with nothing left to send asks the network for nothing, and does not count. That can happen after `error` as well as after `uncertain`. A delivery ends as `error` with its first part on the network unseen when the network stayed out of reach through every retry after the request that got through, when the look that follows a lost answer was answered with a rate limit that names a time more than an hour away, and when the network refused the credentials on that look. After `uncertain` the person should have looked first: if the missing part is on the network after all, trying again publishes it a second time on a network where the server cannot look.
- **What cannot be changed.** A post that is not a draft cannot be edited, in none of its texts, and its channels cannot be changed. That goes for a post that is `scheduled` too: `post.unschedule` makes a draft of it again, which is edited and scheduled anew. A post that is `sending` cannot be deleted either: `post.delete` is rejected with `sending` until every target has ended. Afterwards it can, which removes the post from pigy and nothing from the networks.
- **A channel that is disconnected.** Its `pending` targets are deleted: the drafts no longer go there, and neither do the scheduled posts. A scheduled post that goes nowhere else is a draft again, in the same change. Its targets that are `queued` or `sending` end in `error`, with `disconnected` true, which no other target has: the delivery did not fail by itself. Its targets that had ended stay as they are, with a `channelId` that names no channel any more. A client shows such a target without the account, and `target.retry` is rejected for it with `not_found`.
- **Who writes what.** `target.start`, `target.progress` and `target.end` are the server's, like the mutators of a channel: what a delivery did is the word of whoever did it.

### Scheduling

A post can wait for a time before it is sent. It is `scheduled` then, a status of the post alone: its targets stay `pending` until the time has come. Four fields of the post say when: `mode`, `dueAt`, `queuePosition` and `heldAt`. A fifth, `trashedAt`, says that it was put aside. All are null for a draft and for a post that was published at once.

- **A time that somebody chose.** `post.schedule` sets `mode` to `custom` and `dueAt` to the time. The client checks the text and the channels as it does before `post.publish`, and the server checks them again when it sends.
- **The queue.** A row of `schedule_slot` is a slot: a time of the week, `weekday` and `minute`, on the clocks of the time zone of the workspace. `post.enqueue` sets `mode` to `queue` and gives the post a `queuePosition`. The posts of the queue go out in the order of these numbers, and that is all that they say: they are whole numbers that grow along the queue, with numbers left out where a post has left it, and below zero where a post came to the front. So a post that goes out, leaves or enters at either end changes no row but its own. A client that shows a place counts it. **The mutators keep `dueAt` for the posts of the queue**: the posts take the slots after the time of the mutation, one each, in the order of `queuePosition`. Every mutator that changes the queue, the slots, the time zone or the pause computes the times of all of them anew and writes the rows that change, so a client never computes a time: it reads `dueAt`, and when it runs a mutator for display, the mutator computes on its copy as it will on the server. A post whose `dueAt` has come by the time of the mutation keeps it and takes no slot: the server is about to send it. Time passing changes nothing by itself: the post at the front goes out at its slot and the others have theirs.
- **The order is kept like that of the parts of a thread.** `post.move` names the post to go after and no position, so two devices that reorder at once leave one order behind, and every post has one place and one slot.
- **No time.** `dueAt` is null for the posts of the queue while it is paused, and while the workspace has no slot. They stay `scheduled`, in their order.
- **The pause.** `settings` has one row at most, under the ID `00000000-0000-7000-8000-000000000000`: `timeZone` and `queuePaused`. A workspace without the row has no zone and is not paused. While `queuePaused` is true, nothing of the queue goes out, and a post with a time that somebody chose still does. When the queue goes on, its posts take the slots after that moment: a slot that passed meanwhile was not used.
- **The time zone.** `timeZone` is null until a client sets it, which the app does with the zone of the device, before the first slot or scheduled post of the workspace: `settings.setTimeZone` with `onlyIfUnset`. Until then the slots are in UTC. The mutator stores the zone under the name that whoever runs it has for it: the names of zones are read without regard to case, and a zone can have several, so `europe/rome` is stored as `Europe/Rome`, and `Etc/UTC` as `UTC` where the server says so. What a client holds after the confirmation is the server's name, which need not be the one it sent, nor the one that its own runtime reports for the zone. A client compares two zones by what its runtime makes of both names, `sameTimeZone` in `packages/core/src/schedule/zone.ts`, and not as they are written. A name that the server does not know is rejected with `invalid_arguments`. A slot at a time that the clocks of the zone skip on a day, when they are put forward, is used at the moment that the gap ends plus what the time was into it: 02:30 at the moment that shows 03:30. A slot at a time that the clocks show twice is used at the first. Client and server both compute with the time zone data of `Intl.DateTimeFormat`, in `packages/core/src/schedule/zone.ts`. Where the two differ, because one has newer data, the server's rows are what counts.
- **When the time has come.** The server runs `post.due` for a scheduled post whose `dueAt` has passed: at that time, by an alarm, or as soon after it as it can, and always before it runs another mutation. If the post is at most an hour late, `lateMs`, it is sent as by `post.publish`: the post is `sending`, its targets are `queued`, and it keeps `mode` and `dueAt`, which say when it was to go out. From there it goes the way "Publishing" above says, turns of the channel included. If it is later than that, a post with a time that somebody chose is **held**: it stays `scheduled`, `dueAt` keeps the time that it missed, and `heldAt` is set. It goes nowhere until a client sends `post.publish`, `post.schedule`, `post.enqueue` or `post.unschedule` for it. A post of the queue that is later than that is given the next slot, in its place in the queue. A post that is held or given another slot gets the time of that as its `updatedAt`.
- **One post of the queue at a time.** When the time of several posts of the queue has come, `post.due` for one of them takes up all of them: the first of the queue is sent, if it is at most an hour late, and the others take the slots after that moment, in their order. They are not sent one after the other.
- **A time that has passed.** `post.schedule` takes a `dueAt` in the past: a client can schedule while it has no connection, and the mutation arrives when it arrives. The mutator treats the post like every other that is found late, itself, in the same mutation: sent at once within the hour, held after it. A client that runs it for display does the same by its own clock. So no mutation finds a post that is scheduled for a time that has passed.
- **Sending now, and deleting.** `post.publish` sends a scheduled post at once, and `mode` and `dueAt` are null again. `post.delete` deletes one. The queue closes up behind a post that leaves it, by whichever mutator.
- **Deleting a scheduled post, and taking that back.** A client that deletes a post because it is scheduled does it in two steps. `post.trash` puts the post aside: the row stays, with its parts, its targets and the texts of its accounts, and `trashedAt` is set. A post that is put aside is as good as gone. The server does not take it up when its `dueAt` has come, it has no place in the queue, which closes up behind it, and no `dueAt` there, it does not count among the 500, and a client shows it on no screen. Every mutator but three treats it as a post that does not exist, `not_found`. It keeps `mode`, and what an Undo needs: the `dueAt` that somebody chose, or its `queuePosition`. `post.restore` is the Undo: `trashedAt` is null again, a post of the queue is in the queue at its place if no other post has taken that, and takes a slot with the others, and a post with a time that has passed meanwhile is taken up as `post.schedule` takes one up, sent or held. A post that has lost its last account meanwhile, or for which the workspace has no room among the 500 any more, becomes a draft. `post.delete` with `ifTrashed` is the second step, which a client sends when it no longer offers the Undo. The server takes that step itself for a post that was put aside a day ago, `trashMs`, for a client that never did.
- **Why two steps.** A client can be behind, and without a connection for hours, and the post can have gone out by the time the server hears of the delete: `post.trash` is then rejected with `not_scheduled`, where a plain `post.delete` would remove a post that was sent. And an Undo must never be a second post. Every step is about the one row and does nothing where it does not apply: `post.restore` to a post that is not put aside, `post.delete` with `ifTrashed` to a post that is not put aside, and all three to a post that is gone. So whatever order the steps of one device or of several arrive in, and whatever the server or another device did to the post in between, the post goes out once at most. An Undo that made a copy of the deleted post and scheduled it could not have that: it would have to know that the post it copies was deleted by the very deletion that it undoes, and not sent first and deleted from the record later, and not copied by the Undo of another device as well.
- **A disconnect and a post that is put aside.** `channel.disconnect` takes the target of a scheduled post away, and makes a draft of a post that has none left. Not of one that is put aside: it stays so, and becomes a draft only if it is restored.
- **How many.** A workspace has at most 500 scheduled posts, those of the queue included, and not those that are put aside. `post.schedule` and `post.enqueue` are rejected with `too_many_scheduled` for a draft beyond that. A post that is scheduled already is given another time or place all the same.

Every mutation that a client sends is processed exactly once, and one of three things happens: it changes rows, it changes nothing, or it is rejected. All three are final. A mutation is also rejected, not refused as a message, if its name is unknown (`unknown_mutation`), its arguments are not what the mutator takes (`invalid_arguments`), or its mutator fails on it, which is a bug in the server (`internal_error`). Otherwise a client would send it again for ever, and none of its later mutations would get through. It is another matter when the database of the workspace fails under a mutator, because it is full, for example: sent again later, the mutation can go through. The server then processes nothing of the message and closes the socket with 1011.

The server keeps a rejection until the client has seen it. The patch that answers a `mutate` can get lost, and the rows do not tell the client what happened: an edit that was accepted before its post was deleted leaves the same rows behind as an edit that was rejected because the post was gone. So the answer to the next hello of the client lists the rejections after the `lastMutationId` of that hello, and the server forgets the ones up to it. A client that applies patches the way section 3 says therefore learns of every rejection, and of each once.

Once the server keeps 1,000 rejections for a client, it takes no more mutations from it: it closes the socket on which the next `mutate` arrives with 4401 and does not process that message. The hello on the next socket says how far the client has seen, which makes room. Only a client that has that many mutations rejected on one socket ever notices.

A mutator takes the time from its transaction, which on the server is the server's clock. So a row that a client made for display before the answer can differ from the row that the patch brings, in `createdAt` for example. The patch is right.

The server runs every mutation of a workspace at a time of its own, later than that of the mutation before it: at the time on its clock, or one millisecond after the mutation before if the clock has not moved on since. That holds for the mutations of one message, for messages that arrive in the same millisecond, and when the clock of the server goes back. So the times that mutators put into the rows say in which order the mutations were run, and two rows that were changed by two mutations never tie on such a time.

A client that runs its unconfirmed mutations for display chooses the time of each of them, and the time on its own clock is not good enough. That clock can be behind the server's, and even if it is not, the server gets to a mutation later than the client made it. The server will run the unconfirmed mutations in the order in which they were made, after everything that it has confirmed. So a client runs each of them at a time that is later than every time that a mutator has put into the rows it has from the server, and later than the time of the unconfirmed mutation before it: at the time at which the mutation was made by the client's clock if that is later than both, and otherwise one millisecond after the later of the two. Rows that are sorted by such a time then keep their order when a patch confirms a mutation. Without this, a row that the client has just changed can be shown as older than a row that the server changed before it, until its own confirmation arrives and it jumps. The server keeps its side of this: it runs the mutations in that order, each at a later time than the one before.

Conflicts need no handling by a client. Mutations are applied in the order they reach the server, and a mutator works on the rows as they are then, so of two changes to the same field the later one wins, and changes to different fields both hold.

## 5. How the server works

This is not part of the contract, but it explains its edges.

- **One object per workspace.** A workspace is a Durable Object with a SQLite database, named after the ID of the workspace. It handles one message at a time and everything it does with one is synchronous, so mutations have a single order, and a patch is sent to every socket before the next message is looked at. A socket that a patch cannot be sent to is closed with 1011, so that no client stays connected without a change and waits for nothing.
- **What a client is missing.** The server keeps a change log: for each change, the tables and IDs of the rows it wrote or deleted, not their contents. What a client at cursor N is missing is then the current state of every row that the log names after N: a `put` if the row exists, a `delete` if not. The patch that goes to the connected clients after a change is computed the same way, so there is one path from the database into a message. The alternative, a version number in every row plus tombstones for deleted rows, would need columns in every synced table and a rule for when a tombstone may go. With a log, a synced table needs nothing, and deletions are entries like any other.
- **Keeping the log bounded.** The log covers the last 1,000 changes. A client whose cursor is older gets a snapshot, as does a client with no cursor, and one whose cursor is higher than the workspace's sequence number, which can only come from another workspace or from a workspace that was restored to an earlier state. A snapshot costs as much as the workspace is large, which for text is little.
- **Time.** The object stores the time that it ran the last mutation at, and runs the next one later than that. The clock of a server is not enough: a message brings many mutations in one millisecond, and an object that moves to another machine can find a clock that is behind the one it had. A workspace that is older than this rule begins at the latest time that a mutation has put into its rows, so the rule holds across the upgrade too.
- **Exactly once.** For every client ID the server stores the ID of the last mutation it has processed, in the same transaction as the changes of that mutation. The rows of this table are never removed: one small row per local copy that has ever sent a mutation. The rejections are stored in the same transaction, with a reason of at most 200 characters, and removed when a hello says that the client has seen them. A client that never comes back leaves fewer than 1,100 behind.
- **Rejected or failed.** An error is the database's own, and aborts the message, if SQLite reports that it could not do its work whatever it was asked: it is full, cannot be read or written, is locked, or has no memory. Every other error while a mutator runs is the mutator's, and the mutation is rejected for good: an error that the mutator throws, and one from the database about what the mutator wrote, such as a constraint that a row violates or a value that is too large. Those would come again however often the mutation was sent.
- **What can be synced.** Each synced table has an explicit list of synced columns, in `apps/worker/src/workspace/synced.ts`, and every row in a patch is read through it. A column or a table that is not listed cannot get into a message. The credentials of a channel are such a column. The object does not hold them in the clear either: the Worker seals them before it hands them over.
- **Whose a mutation is.** The object runs a mutator for a client, when a `mutate` arrives, or for the Worker, which calls it directly. It tells the mutator which, and a mutator of the server's own refuses a client.
- **Scheduled posts.** The alarm of the object is set to the earliest `dueAt` among the scheduled posts that are not held and not put aside, and nothing polls. It also runs a day after a post was put aside, to delete it: `post.delete` with `ifTrashed`, which the clients hear of like of any change. Before the first mutation of a message and after each of them, and when the alarm runs, the object runs `post.due` for the posts whose time has come. So a mutation never finds a post that should have gone out by its time. Between the mutations of one message it is as between two messages: what becomes of a post does not depend on how a client packs its mutations into messages.
- **Deliveries.** The object begins the deliveries, one at a time per channel, and a workflow carries each out and reports to the object, with the mutators of the server's own. The object goes by its database alone: which targets wait, which are on their way, and for which it has started a workflow. An alarm starts the workflows and ends a delivery whose workflow has stopped without reporting. `PLAN.md` section 8 has the design.
- **The inbox and the devices.** A notification is a row like any other, written by the mutators above. For every notification that a mutator makes, or makes anew, the object queues a push message in the transaction of the change, and its alarm sends the queue to the devices of the owner, without keeping a delivery waiting for a push service: `PLAN.md` section 13. The alarm also runs `channel.warnOfExpiry`, when the time of an access has come, and `notification.prune`.
- **Calls with a key.** The Worker can name a call that changes the workspace with a key. The object carries such a call out once and keeps its outcome under the key, in the transaction of the change, so that a caller which tries again cannot make a change twice.
- **Hibernation.** The sockets stay open while the object is not in memory. What the object knows about a socket, its client ID and when it runs out, is stored with the socket, and everything else is in the database.
- **Who is asking.** The object does not see the client's request. The Worker makes a new one that names the workspace, after it has checked the session and the owner. The object remembers which workspace it holds from the first time it is used, and refuses to serve another.

## 6. What is not covered

- Messages are not rate-limited, and nothing limits how much a workspace stores. Both are bounded only by what one signed-in user does to their own workspace.
- A client cannot ask for part of a workspace: it holds all of it.
- Deleting a post removes it from the workspace and nothing from the networks: what it published stays published.
- A part that is removed is gone: a client that offers to bring it back adds a new part with its text.
- When the schema version changes, a client of the new version drops its rows and says hello with the cursor `null`, unless it knows how to convert them. It keeps its client ID and its `lastMutationId`. Its unconfirmed mutations are sent as they are, and rejected if the new mutators do not take them.
- If the data of a workspace is ever restored to an earlier state, clients whose cursor is ahead get a snapshot, but a client can stay ahead unnoticed if the workspace then catches up with its cursor. Restoring has to come with a way to make every client start over, such as a new schema version.
